## 5. Review and workspace

A single accountable implementer owns each coherent PR. For routine changes, there is no compulsory independent Tech Lead review, separate reviewer identity, reviewer assignment, or reviewer receipt. The implementer must verify the exact candidate diff, relevant canonical contract, directly affected consumers and same-head CI/proof before merging, and may request a bounded independent review when useful. Additional review is required only when a specific Jira authorization, protected action, or enforceable GitHub rule says so; a required native approval must come from a genuinely eligible separate identity. Do not invent approvals or attempt to bypass repository protections. If a review is performed, record the exact reviewed SHA and a consolidated decision in the existing PR. When the head or relevant base moves, repeat only the affected checks. Escalate genuine security, destructive-behavior, architectural, or acceptance conflicts to their actual owners, not to an automatic reviewer-assignment loop.

When the next required action belongs in Codex, Claude Code, or equivalent, the Tech Lead response must include the exact executable handoff prompt in that same response. Do not send a status-only message that forces Jim to ask for the prompt separately unless Jim explicitly requested status only.

Use a clean intended base/worktree; do not repair/reset an unrelated dirty workspace. Normal handoff is the remote Git candidate with exact base/head and proof. One failed execution path gets one approved fallback; if both fail report `ENVIRONMENT_BLOCKER — STOP`. Do not cycle clone methods, archives, base64, screenshots, patch fragments, sandbox-only transport, or manual reconstruction.

## 6. Coordination, Notion safety, retry

Claims exist only for real concurrent-write collisions. Read Development Projects immediately before ownership or takeover questions, or when overlapping writers are plausible; when a claim is required, claim exact mutation surfaces only. Never create a lock database, heartbeat, watcher, scheduler, or coordination service.

For Notion database/data-source querying, bulk QA, reconciliation, counts, duplicate detection, or migration analysis, follow the conservative query order defined here (V1 policy is reference-only): `exact fetch → saved mode=view → repository-owned/Public API snapshot → metered rows/SQL only with Jim's explicit per-query approval`. A surrounding “go,” development approval, debugging need, or emergency never authorizes metered querying.

One failure boundary gets one retry owner; retry the smallest unit once when useful. Production retry semantics live in V7's current runtime implementation and applicable approved V7 contracts. Do not add infrastructure, recovery frameworks, QA generations, or investigation programs in response to failure. Stop at the time boundary.

## 7. Completion

Every landed package reports only **OUTCOME**, **REMOVAL**, **PROOF**, **REMOTE SHA**, and **NEXT**. A completed package must make the live product easier to understand or leave it no more complex; if governance is needed to tolerate implementation complexity, simplify the implementation. `LANDED` means intended branch plus targeted proof; it is not production-ready, accepted, or closed. For unattended/runtime/connector changes, identify before implementation and later prove: `trigger → available transport/tool → mutation owner → canonical persisted state → authoritative read-back`. No design may depend on an unshown tool, permission, transport, payload, credential, or mutation capability. Manual/operator execution, mocks, and alternate paths do not substitute for unattended acceptance.

`LANDED` = code is on the intended branch and targeted proof passed. `TARGETED PROOF FAILED` reports the exact named proof failure. `BLOCKED: <exact dependency>` reports the concrete dependency preventing safe completion. `ACCEPTED` = the changed production boundary executed successfully and authoritative resulting state was read back and verified. `CLOSED` = ACCEPTED with no known defect or recovery debt in the promised outcome. `DEGRADED` is fail-closed, never completion; an active defect remains active until it converges to PASS or Jim explicitly reprioritizes an external blocker. Do not begin an unrelated roadmap package merely because work LANDED.

## 8. Budgets and mandatory metadata

**File budget:** ChatGPT and Codex may touch at most three production files per package; obtain Jim's explicit approval before touching a fourth. Claude Code has no production-file limit for a coherent, approved package (§3 Bounded autonomy).

**Line budget — ChatGPT, Codex and Claude Code:** ChatGPT and Codex have a **300 production-line cap** per package; Claude Code has the same cap except during the temporary Jobs OS/Interview OS exception below, which ends when Jim records LIFE-107 and LIFE-106 accepted in Jira or earlier revokes it in a Jira comment. Production-code deletions are free. Above the applicable cap requires Jim's explicit scoped approval and `Jim-Approved-Budget: <justification>` in the commit message. Prefer deletion/reuse for repairs; explain necessary positive net production LOC rather than fragmenting a sound vertical slice. ChatGPT/Codex default test surface is two files; Claude's end-to-end package may use the test files actually necessary to prove its approved outcome, without a mechanical test-file limit. For work subject to the cap, after three accepted substantive Claude end-to-end deliveries, the Career/Jobs Tech Lead and Jim review delivery speed, defects, readability and diff sizes and consider reducing the threshold. Any reduction requires Jim's explicit approval and a new edit of this same canonical policy; no automatic decrease or new governance artifact.

**Usage budget:** Codex has a 2% limit per active five-hour allowance window (1.8% early warning). Claude Code may use up to 10% of the five-hour allowance per approved package (9% early warning), within the existing subscription only. No paid API use, credits, upgrade or external spend. If usage telemetry is unavailable, do not claim the budget is verified; avoid speculative broad exploration and preserve the working candidate when the applicable cap is reached. Tech Leads compile exact repo/base, affected boundaries, expected proof and stop conditions for short-run metered work. ChatGPT/Codex major-feature acceptance attempts retain their 60-minute SLA: reassess at 30, remove nonessential work at 45, prepare acceptance at 55, stop at 60 as `TIMEBOX_STOP` with the blocker. **Claude Code end-to-end budget:** Claude has no production-file limit. Its 300-line cap is suspended by the temporary Jobs OS/Interview OS exception above until Jim records LIFE-107 and LIFE-106 accepted in Jira, or revokes the exception in a Jira comment; the cap then applies again automatically. Claude's 10% usage cap is defined above. Record `Claude-End-to-End: LIFE-<issue>` in the PR description. Preserve normal quality, concurrency, privacy, release, authorization and production-spending gates. If repo-local checks still enforce superseded limits, report the exact check and request a narrow policy-alignment correction; do not bypass CI or weaken the Codex file-count or spending gates.

Tests are budgeted by execution cost and protected behavior, not collected count. There is no numerical repository test-count ceiling and no `Production-Critical-Test:` commit-metadata requirement. The complete deterministic repository test suite must complete in under 90 seconds on the standard CI runner; this applies to the deterministic repository suite itself, not total CI elapsed time or targeted live/external acceptance. CI should surface a soft warning beginning at 45 seconds and must fail when deterministic suite runtime reaches 90 seconds. Tests protect accepted user-visible paths, continuing relevant regressions, canonical contract boundaries, or necessary fail-closed controls; remove obsolete tests with removed behavior, retired internals, duplicated implementation detail, superseded runners/QA phases, or behavior already protected by a stronger canonical boundary. New implementations of an existing composable boundary should reuse the owning behavioral contract wherever practical instead of creating duplicate implementation-specific suites. Test count is not a quality metric. Use the smallest targeted proof during implementation, affected regression once, and the complete deterministic suite at most once on the final deterministic candidate; then rely on CI. One implementer owns one package; do not duplicate rediscovery.

A package may declare `Production-Frozen: true`; then production code, configuration, and workflows are outside its surface, any such diff is `SCOPE_EXPANSION_STOP` and must fail repository enforcement where supported, and incidental runtime changes are not allowed. Production mutation becomes a separately scoped package. Repo CI may be stricter but may not weaken these rules without Jim's explicit approval.
