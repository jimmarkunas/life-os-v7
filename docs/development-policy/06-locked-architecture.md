## 2. Locked architecture and execution constitution

LIFE OS is one unified composable platform: one live implementation per behavior; product flows are explainable as `Acquire → Normalize → Decide → Persist → Present`, with stages combined or absent when unnecessary; domain policy stays with its owner and shared infrastructure owns only reusable mechanics. Reuse before abstraction: do not introduce a framework, dispatcher, adapter layer, shared base class, orchestration layer, or utility abstraction for one consumer. Do not create a replacement platform, second repo architecture, second scheduler service (multiple human-approved GitHub Actions workflows in the existing V7 infrastructure are not one), second orchestration stack, or duplicate datastore/source of truth without Jim's explicit approval. When a replacement works, remove the superseded live path in the same coherent package whenever safe. Current behavior must not depend on milestone-era numbered QA namespaces; when that boundary is touched, move still-needed behavior into its owning product domain. Git is the archive: production source does not retain obsolete implementations, one-shot recovery utilities, investigation code, stale milestone artifacts, or historical compatibility paths merely for reference. Runtime dependencies belong in the canonical dependency declaration where practical; isolated runtime dependencies may have their own declaration, but workflows/scripts may not inline packages.

Only Jim may supersede these locked rules. A conflicting request or path stops with:

`ARCHITECTURAL DRIFT DETECTED — NO MUTATION`

The non-mutable execution constitution is:

1. The current Production Contract controls scheduled and runtime behavior. `LIFE OS Daily Runs` is retired (Part 01 Status); V7's existing GitHub scheduled workflows issue the minimum deterministic trigger, and approved code owns deterministic execution, recovery mechanics, classification, and lane orchestration.
2. Standard public GitHub-hosted Actions in the public `jimmarkunas/life-os-v7` repository are the sole approved scheduled execution infrastructure and an approved stateless executor when triggered by an approved schedule or an authorized operator; the Production Contract is the one authority that approves each schedule. Multiple independently triggered bounded workloads may run without waiting for unrelated workloads. Each needs an explicit human-authorized workload and cadence, one authoritative owner, exactly one canonical writer for every workload that writes (read-only workloads need no write permission), declared dependencies, a provider budget, bounded retries, idempotency, a checkpoint with missing- and duplicate-run recovery, independent complete, degraded and incomplete receipts, and a rollback. The existing hourly tick and its domain workflows continue unchanged, so V7 runs correctly with ChatGPT unavailable (D54). This rule authorizes no additional workflow, larger or paid runner, credential movement, scheduler service, duplicate datastore or production trigger. Actions artifacts/caches are neither canonical state nor required production handoff storage; production secrets/private payloads must never enter Git history, logs, artifacts, or caches.
3. Diagnose runtime failures in this order: `trigger → runtime actually started → code ran → source accessed → canonical state persisted → authoritative read-back`; if an earlier boundary failed, do not debug downstream product logic.
4. One failure boundary gets one retry. A second failure stops the run for boundary/architecture diagnosis; do not cycle retries, transports, or alternate paths.
5. If a simple operation needs more than two cycles or roughly ten minutes of active debugging, stop and challenge the architecture, execution boundary, or executor before adding machinery.
6. ChatGPT owns scheduling, judgment, product decisions, architecture, decomposition, bounded handoff, review, approval-aware orchestration, and acceptance; approved code owns deterministic production execution, recovery mechanics, classification, and lane orchestration. Repository-heavy work belongs in Codex, Claude Code, or equivalent. Before substantive work, route multi-file mutation, nontrivial code/config refactoring, local test loops, large documentation/config rewrites, broad inspection, bulk evidence generation, or work likely to exceed two connector cycles/five minutes by telling Jim: **`Do this in Codex or Claude Code.`** Direct ChatGPT execution is limited to clearly tiny, reversible, surgical work whose complete affected surface is safely inspectable and has complete deterministic proof in the Fast Path.
7. Do not add compensating trigger-file RPC, recovery, workflow, coordination, scheduler, dispatcher, or orchestration machinery for a brittle boundary without Jim's explicit approval.
8. Prefer subtraction over repair: remove or bypass unnecessary machinery before hardening it.

Before creating a new scheduler/workflow, new datastore/source of truth, second live implementation, generic framework/orchestrator/dispatcher, numbered QA hierarchy, permanent recovery subsystem, new development/governance artifact, or shared abstraction with only one real consumer, stop for explicit Tech Lead architectural review. A locked-architecture conflict reports the exact phrase above.
