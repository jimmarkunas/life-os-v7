### LOS-first discovery and description-first requirements — Jim-approved November 1, 2026 (LIFE-79)

This is an agent intake and readiness contract enforced by this policy, its contract tests and read-back. It adds no scheduler, backlog, store, Jira workflow, schema change or automation.

1. **LOS first.** A new product idea, initiative, tool adoption, capability or product-changing requirement starts in an existing relevant LOS Idea (search first; create one only if none exists), with its product owner and owning Notion requirement. No LIFE feature Epic, Story or Task is created or released for a new product outcome until Jim has co-scoped and approved the LOS requirement for delivery, mapped it to a suitable LIFE Epic or an approved new finite Epic, and linked origin and acceptance. A parked LOS Idea is not delivery authorization. **Exception without bypass:** maintenance, bugs, scoped technical tasks and in-scope children of an already approved finite Epic cite that approved parent or Epic and need no duplicate LOS Idea; a claimed exception cannot launder a new product outcome. On premature creation or release, answer `DISCOVERY_NOT_READY — <LOS key or missing approval/trace>`, keep the gathered requirements in LOS and stop. Jira's create API does not enforce the LOS-to-LIFE relationship: **NOT TECHNICALLY ENFORCED**.
2. **Persist discovery answers.** Start each discovery chat by reading the exact owning LOS Idea and its Description; there is no chat-only discovery. After each owner reply and before the next tranche, update that same LOS Description in place with every answered question: question number, the owner's answer faithfully, decision state (`APPROVED DECISION`, `PROPOSED`, `UNRESOLVED` or `FEASIBILITY TO VERIFY`), requirement impact and open gap, under `Discovery log — Tranche N (owner reply date)`. Approval is never inferred from an assistant recommendation. Preserve earlier approved sections and correct a changed answer in place with dated supersession context. Then re-fetch the issue and compare every answer to the saved text. If the write or read-back fails, report `DISCOVERY_CAPTURE_BLOCKED` with the missing question numbers and stop asking questions; never rely on chat memory or a comment. Final approved durable requirements are consolidated in the owning Notion page at the product handoff.
3. **Description is the requirements source.** The LOS Description holds the interview, answers, approvals and unresolved items; the LIFE Description holds the bounded outcome, scope, non-goals, dependencies and acceptance contract; Notion holds approved detailed requirements. Jira comments are for active development only (run findings, blockers, handoff, review and verification receipts); a planning answer, scope decision or requirements update is never comment-only. A stale comment never outranks a current Description.
4. **Acceptance checklist.** Every acceptance behavior is a separate numbered `Given / When / Then` item with a proof state (`[ ]` or `[x]`) and cited evidence; a `[x]` without real cited proof is invalid. A Smart Checklist may replace the visible text checklist only after its presence, field/API, permissions, checkbox semantics and read-back are verified on this Jira site and one authoritative completion state is kept; on this site that is **UNVERIFIED**, so the LIFE Description text checklist is the canonical form and is not an interactive Jira checklist. A tick, app percentage, green PR check or merge is never Done: completion needs authoritative evidence and the applicable Agent UAT, Human UAT or approval.
5. **Handoff gate.** Before a fresh-agent implementation handoff, re-read the owning LOS, Notion and LIFE records and verify the approved LOS origin (or a cited exception), a non-duplicated delivery item, every recorded answer, complete Given/When/Then items, execution owner, blockers, human prerequisites and stop conditions. Otherwise return `DISCOVERY_NOT_READY` or `QUEUE_NOT_READY` with the exact missing fields.

Agent Go release, Priority order, claims, one-writer scope and protected-operation gates are unchanged.

### Context efficiency — Jim-approved November 1, 2026 (LIFE-79)

This lowers context use, repeated reads and duplicated documentation without weakening requirements, approval authority, historical evidence or independent verification. It is agent policy behavior; it adds no task store, scheduler, dispatcher, index, context-sync service or agent relay.

1. **Minimal retrieval.** Read the owning Jira issue first. Then fetch only the specific Notion section, GitHub file or related Jira issue needed to resolve a real dependency. Never pull whole conversation histories, unrelated tickets or long documents by default. Reuse already verified context while its source revision is unchanged, and stop researching once sufficient authoritative evidence exists. Read again when the revision changed, new evidence is required, or safety, authority, a contradiction, missing proof or verification calls for it.
2. **Ownership, no duplication.** The LOS Description holds concise current discovery decisions, owner answers, unresolved questions and authoritative links. The LIFE Description holds implementation-ready scope, `Given / When / Then` acceptance, dependencies and execution instructions. Notion holds detailed product specifications, architecture and durable rationale. GitHub holds code, technical policy and implementation and verification evidence. Comments hold active development findings and receipts, not requirements. Link to the owner instead of copying; never move, delete, summarize away or overwrite previously approved decisions or historical evidence.
3. **Interview persistence.** Read the owning LOS issue at interview start and do not re-fetch Notion during routine questioning. After each owner reply, write every answered question and its decision state into the existing LOS Description with a narrow edit; if the issue's revision changed since it was read, re-read and merge so another writer's update is kept. Independently read the change back before the next tranche. Failed persistence or read-back returns `DISCOVERY_CAPTURE_BLOCKED` and stops the next tranche. Consolidate approved detailed requirements into Notion at the agreed product milestone.
4. **Proportional budgets.** Prefer the smallest read set that is sufficient, within the §8 budgets and Fast Path, and avoid large repeated payloads. A token, time or call budget never overrides correctness: extra reads are required for safety, authority, source revisions, contradictions and verification.
5. **Fresh-agent handoff.** A fresh agent recovers the approved current scope from one Jira key and its authoritative links, without pasted conversation history. A missing prerequisite returns the specific `DISCOVERY_NOT_READY` or `QUEUE_NOT_READY` failure rather than speculative implementation.

Repository contracts verify this wording and the schema's handoff and read-back fields; they cannot observe or limit an external agent's tool calls, so retrieval behavior stays agent policy. Agent Go release, Priority order, claims, one-writer scope and protected-operation gates are unchanged.
