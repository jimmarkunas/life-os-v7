## 3. Bootstrap and outcome-bounded execution

**ChatGPT and Codex only:** Coding runs are hard-bounded to five minutes, including bootstrap, inspection, mutation, and targeted proof; at five minutes stop as `LANDED`, `TARGETED PROOF FAILED`, or `BLOCKED: <exact dependency>`. This five-minute rule does **not** apply to Claude Code. For ChatGPT/Codex, split only on meaningful independently provable boundaries, never meaningless micro-tasks. External runtime/connector/CI acceptance may continue separately.

### Claude Code end-to-end delivery mode — Jim-directed October 17, 2026

For a Jim-authorized, sufficiently scoped LIFE Jira issue, the **single designated repository-heavy Claude Code implementer** owns the coherent vertical-slice outcome in one sustained execution: inspect the relevant implementation, build across needed modules, repair defects, run targeted and final deterministic proof, open/update the candidate PR, and address same-issue review corrections. **One approved Jira outcome → one sustained implementation effort.** Do not impose artificial implementation stops, arbitrary line-count increments, arbitrary test-file limits or repeated Tech Lead micro-handoffs. Claude's package budgets (the production-line cap, its temporary Jobs OS/Interview OS exception, and the usage cap) are owned by §8. Claude has no production-file limit: it is the system-wide implementer and must keep whole-system context, so a coherent package touches every file its outcome needs. A package needing more than its §8 caps requires Jim's scoped approval, not artificial fragmentation. Without that approval, stop spending at the usage cap while preserving the working candidate. The approved Jira outcome, canonical contracts, architecture, single-writer ownership and repository scope remain controlling. No new paid capacity, API charges or unauthorized tool usage is implied.

Preserve the warm workspace and continue the same approved issue until a coherent candidate is ready or a real stop condition applies. Run the complete deterministic suite at most once per final candidate and use exact-head CI and any review explicitly required by GitHub or the approved issue. **Completion stop:** the issue targets one user outcome. Stop implementation when its acceptance criteria pass, required proof is complete, and no material defect remains. Do not continue subjective polish or expand scope after that point; record optional improvements as a separate proposal for Jim's approval.

### Bounded autonomy — one approval per delivery objective — Jim-approved October 23, 2026 (LIFE-79)

1. One Jim-approved Jira outcome or named delivery train authorizes its owner to inspect, implement, repair, test, open/update the PR, answer review and return the receipt in one session. No re-asking for module boundaries, file counts, line counts within §8, implementation choices, CI repairs, review iterations or continuing the same objective. One coherent PR per issue. It never covers another owner's surface, a protected action or unrelated backlog.
2. Budgets are §8. Within them, ask nothing; Claude never asks about file counts, and never about line counts while the temporary Jobs OS/Interview OS exception is active. Never split one dependency into micro-PRs; above a remaining cap, ask once with the exact need.
3. **Routine authorized merge without compulsory independent review:** the assigned implementer or authorized operator may merge a routine, nonprotected PR when the issue scope, current base/head, targeted tests, full same-head CI, ownership, and relevant negative/regression checks pass. Independent Tech Lead review is optional unless the approved Jira issue, a specific protected operation, or native GitHub branch protection expressly requires it. Do not fabricate or impersonate a GitHub approval, bypass branch rules, or treat merge as deployment authority. Secrets, permissions, production deployment/activation/dispatch/switches, user-data changes, and acceptance Jim reserved always retain their separate explicit gates.
3a. **Protected-file merge by Claude Code — Jim-approved October 24, 2026; amended October 30, 2026; lane guard retired November 1, 2026:** The LIFE-78 lane guard (its workflow, `lifeos/lane_guard.py`, ownership/handoff maps, per-PR exemptions and `jobs-e2e` train restrictions) is retired on Jim's explicit authorization and no longer gates PRs. Claude Code may merge its own PR only when required same-head unit-tests and all enforceable native GitHub protections pass, and any additional protected-action authorization has been recorded in the existing Jira issue or PR. Independent technical review is not an automatic extra policy gate; when native GitHub protection or a specific owner-approved condition requires another eligible approver, that requirement remains binding. This never extends to secrets, permissions, branch-protection or repository settings, production activation/dispatch/switches, user-data changes, or acceptance Jim reserved.

**Permission and safety boundaries remain unchanged:** fresh-main/delta checks, approved product behavior, test quality, fail-closed evidence, the Runtime Completeness Gate, required Jim review/acceptance, and separately authorized production merge/dispatch, live Gmail/Notion or other source mutations, schema/scheduler/security changes, model spending and external private-data transfer. This mode does not authorize a new runtime, datastore, scheduler or overlapping agent. A genuine blocked gate stops only the affected action; complete the remaining safe implementation within the same package.

Bootstrap uses the smallest live context. Start from V7 `AGENTS.md` as the routing index, then read this policy; the exact LIFE Jira ticket and linked LOS idea where one exists (consult the legacy V7 WBS row only for technical scope/evidence not yet on the Jira ticket); the one relevant current product/domain canon or section; `CODEMAP` only when repo navigation is needed; and the exact affected implementation/direct callers. Read the Production Contract only when runtime facts are needed and Development Projects only for ownership/concurrency. Do not perform broad repository audits, historical searches, broad dependency archaeology, coordination reads, or secondary reviews unless a concrete fact makes them necessary. If implementation has not begun and no concrete blocker exists, stop reading and implement. Before implementation or code-review analysis, fetch `origin`, record current `origin/main`, and if main moved inspect only the affected delta; if it changes the claimed surface stop with `BASE_MOVED_STOP`. Before mutation also verify the correct repo, intended current base, no unrelated diff, and exact mutation boundary.

Fast Path: define outcome; name mutation surface/direct callers; name smallest failing proof and negative control; inspect narrowly; mutate once; remove directly superseded local code; prove once; land or stop. A concrete dependency outside the boundary may be added only if trivial and within the cap; otherwise stop with `BLOCKED: <exact dependency>`. No silent scope expansion or neighboring cleanup. Clean-as-you-touch covers only directly obsolete local code, tests, fixtures, wrappers, imports, and duplicate paths; new semantics, architecture, or budget requires rescoping.
