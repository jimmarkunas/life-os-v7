### Deterministic agent work selection — mandatory when an authorized execution session starts or resumes

This is a **pull rule**, not a ChatGPT dispatch queue. When an authorized coding agent is invoked, resumes its package or finishes a Jim-accepted one, **the agent** picks the next eligible LIFE issue from live Jira. ChatGPT does not nominate issues or write handoff prompts. Instructions alone do not wake an idle session, and a Jira status change (including release to `Agent Go`) does not by itself start a dormant agent: use only an existing approved invocation, never a new scheduler, poller, watchdog or dispatcher.

1. **Resume first.** Fresh-read your active LIFE issue, its PR/head and, where writers may collide, your lane claim in Development Projects. An unfinished package is sticky until accepted Done, formally blocked or reassigned.
2. **Select from the Agent Go queue, not documents.** `project = LIFE AND status = "Agent Go" AND issuetype != Epic ORDER BY priority DESC, Rank ASC`, in your lane. Nothing outside Agent Go is selected autonomously, and an agent promotes work into `Agent Go` only under the self-promotion rule in the lifecycle section below. Skip, without any Jira change, issues with an incomplete incoming `Blocks` predecessor, missing or invalid owner or lane, a conflicting or already-claimed writer, an execution environment the agent does not support, a parked or unapproved product, another lane, or unverifiable authorization. A candidate needs an owning Epic, clear authorization (an individual approval, or a child recorded and read back inside an approved Epic's envelope) and a known lane. `To Do` or a linked LOS idea authorizes nothing. Release leaf issues only; an issue with children is a container.
3. **Order is Priority, then Rank.** Rank breaks ties, including at the default Medium. Humans set both; agents never reprioritize or reorder. No WBS order, creation date, key order or cached snapshot. A contradiction → `QUEUE_NOT_READY`.
4. **Start.** Re-read status, blockers and scope; keep one writer per mutation surface (Concord `start_work`/`finish_work` are optional, never a refusal). Make the supported transition Agent Go to In Progress (ID 14, "Start work (authorization receipt required)"), verify the read-back, then run the lifecycle below. Moving a ticket to Agent Go IS Jim's approval.
5. **Fail closed.** If access, authorization, lane, readiness, order or predecessors cannot be established report `QUEUE_NOT_READY — <exact gap>` and stop; do not ask ChatGPT to pick, invent a priority or use a snapshot. An empty `Agent Go` queue is `NO_ELIGIBLE_WORK` with no mutation and no pull from To Do.
6. **Completion.** PR/CI success is `LANDED`. After merge, receipt and read-back, the implementing agent moves the issue to Done (delegated closeout is the default); Jim reopens it or files a Bug. Then the same session repeats selection.

**Queue readiness.** Jira must hold usable lane ownership, curated order, truthful statuses and issue-level dependency and approval evidence; documenting this selector does not make a board executable. Repair planning data in Jira without creating another source of truth, and never mass-assign or reorder inside a development session.

**Lane labels (October 13).** `lane-career-v7` and `lane-edge-comm` identify the two authorized lanes; the lane label is the routing and ownership field and the assignee may stay Jim (agents are not Jira users). Only the Jira planning owner applies or changes lane labels, with one delegation: the approved lead of a specifically authorized finite Epic acts as planning owner solely for new, in-scope children of that Epic (lane, owner, dependencies, Priority, Rank), verified by read-back before execution. It never lets an agent release into `Agent Go`, never reaches other tickets and never overrides blockers, acceptance, affinity or the one-writer claim.

**Release simplification — Jim-approved November 4, 2026.** (1) Jim's authenticated instruction naming the issue and scope starts that work without an Agent Go release; `authorization.provenance` records channel and time. (2) A whole `Blocks` chain may be released in one bulk transition; the links and this selector sequence it. (3) Readiness minimum: a valid key, at least one Done-when line (a Given/When/Then row or a bullet under "Done when") and every `Blocks` predecessor Done; everything else is a `warn` line (`python -m lifeos.sources.devtools.readiness`). (4) For an Epic Jim approved with a written non-protected scope, its approved lead may release in-scope children it creates into Agent Go; protected steps stay owned human Sub-tasks that block the work. This is the only relaxation of "agents never promote"; strike it to keep human-only release.

**Scoping.** One planning pass per Epic: write executable Tasks with Given/When/Then, a fast-proof command, `Blocks` links and protected-operation permissions, run the readiness validator on each, turn every gap into a fix or an owned human Sub-task, then stop; approved scope is not re-litigated.

### Jira-first development lifecycle — mandatory across ChatGPT, Claude Code, Codex and approved Edge implementers

1. **Intake.** New product outcomes come from the current LOS idea (moved out of Parking lot only on Jim's prioritization); bugs and maintenance start directly as LIFE issues under the owning Epic. Reuse an existing issue; never create a parallel planning record.
2. **Read the live issue before accepting work:** key, parent Epic, status, blockers, scope, acceptance boundary, WBS ID and linked LOS idea, plus the owning Notion canon and only the technical contracts that apply. The frozen roadmap cannot settle priority or state. No ticket or ambiguous scope: the Jira owner reconciles or creates the narrow issue first.
3. **Ownership.** Read Development Projects only where overlap is plausible; keep one repo-heavy writer per mutation surface. Set In Progress only when execution actually starts, with read-back; never from a prompt or branch name alone.
4. **Implement** in the approved workspace within this policy's scope, architecture, permission and proof gates. Put the LIFE key in the branch, PR title and commits (format: the issue-writing contract), keep the WBS ID and LOS links, one bounded branch and PR per package.
5. **Report truthfully.** A ticket is Done when its PR is merged on same-head green CI with local proof. Live acceptance is a watch, never a gate. Update Jira only from verified evidence.
6. **Close.** After merge, receipt and read-back the implementing agent moves the issue to Done (delegated closeout is the default for every non-protected ticket); Jim reopens it or files a Bug. Update product stage only to match real approved state.
7. **Jira unavailable.** Autonomous selection needs fresh Jira access. A verified exact-issue handoff supports one specifically authorized implementation but is not live Jira access or permission to mutate Jira; if scope, dependency or owner state cannot be established, fail closed for that action and name the gate. No GitHub or Notion status snapshot, no sync service.

**Delivery flow v3 — Jim-approved November 9, 2026.**
- **One ticket, one approval.** Moving a ticket to Agent Go is the approval and covers everything inside the written scope; at release the releasing session lists every approval the ticket is known to need (protected files by name, workflow edits, Oracle run lines, model spend, host steps, secrets) in one comment to Jim and records his answer as one `[approvals]` line (files, answer, `ct_stamp` time); a builder that finds a new need stops and asks once, naming it. When a release batch holds several tickets that edit `.github/workflows`, the releasing session groups those that touch the same workflow file into ONE PR and one approval ask (one workflow PR open at a time stays; the label `protected-file-approved` only on Jim's typed yes). A change of plan is an edit to the ticket plus one line `Scope change: <what> — Jim, <time CT>`; the description beats comments. A scoping note is one page (at most 2,000 characters: Outcome, 3 to 5 Done-when checks, Not in scope); one execution ticket is one PR or one sheet edit.
- **One receipt.** A builder opens its PR, waits with `gh pr checks <n> --watch --interval 30` and merges within 5 minutes of same-head green with `gh pr merge <n> --squash --match-head-commit <sha>`; if it cannot, it posts `[waiting on] <reason>` on the ticket. After merge post one comment: PR link, what changed, how it was verified, what is unverified. The agent moves the ticket to Done. Label `needs-uat` means stop at Human UAT with exact steps for Jim (new user-facing UI or judgment only).
- **Ticket truth.** The claiming agent edits its ticket in the same session that reality changes; a superseded ticket is Cancelled with a line naming its replacement. A session that claims a ticket posts `[claim] <session> <ct_stamp time>`; on any pause or hand-off it posts `[waiting on] <Jim, CI, another PR or ticket by key, a host step, or no free session>, <CT time>`, so no stretch of 60 minutes or more on an Agent Go ticket is unexplained (`python -m lifeos.sources.devtools.record_gaps FILE` lists such stretches from a saved Jira export; no timer, watcher or scheduled job).
- **Transitions.** Any status can reach any status so agents are never stuck. To Do and Agent Go reach In Progress only through ID 14; every other status uses "Resume work".

**Lean delivery — Jim-approved November 15, 2026 (LIFE-726).** This amendment overrides any conflicting text in these parts, in AGENTS.md and in Jira comments. It removes ceremony and keeps every real safety gate.
- **Approve by risk class, once.** A change merges on same-head green CI with no label, no file list and no typed yes unless it does one of these four things: (1) adds or widens a workflow `permissions` block or any write permission; (2) adds, moves or exposes a credential (a Bitwarden load, a `secrets.` reference, a token reaching a job that did not have it); (3) deletes a GitHub value or production data; (4) spends money or runs a paid model beyond the ticket's approved budget. For those four, Jim says yes once, asked at release or the moment the need is found, and the session records it as one `[approvals]` line. **The `protected-file-approved` label and its CI check (`.github/protected_files.py`) are removed (Jim, November 15, 2026: "completely get rid of this protected-file-approved"); the four files it guarded (`.claude/settings.json`, `docs/PRIVACY.md`, `tests/contracts/test_privacy.py`, `tools/push_life_branch.sh`) are ordinary files, and the privacy test itself still runs.** Editing a workflow file is not by itself a protected class, and a test or registry edit that follows from an approved change needs no further approval so long as no check is loosened. Workflow PRs that edit the same file are batched or rebased in order; "one workflow PR open at a time" is no longer a rule of this policy (a project freeze such as LIFE-686's stays until Jim lifts it).
- **One Jira receipt per ticket.** Moving the ticket to In Progress (transition ID 14) is the claim; there is no start comment. One receipt comment at the end (PR link, what changed, how verified, what is unverified). A comment mid-ticket only when it is really waiting on Jim: `[waiting on] Jim: <the one thing>`, with a chat message. No pause stamps and no takeover note: if a session is gone, any session continues its branch and says so in its receipt. One writer per branch at a time still holds.
- **Lanes are hints, not gates.** Any session may take any Agent Go ticket, top Priority then Rank. A `lane-*` label says who usually builds it; repository and host affinity stay a preference, and a session that cannot run a step (a host it cannot reach) says so and leaves that one step.
- **The registries write themselves.** Adding a stage or package is its code plus `python tools/regen.py`, which adds the rows the contract tests mirror; hand-written content (code meanings, measured budget bases) stays hand-written.
- **Merge is Done; auto-merge by default (LIFE-728, LIFE-729, Jim, Nov 15 2026: "Build all three").** A PR that touches none of the four gated items has auto-merge enabled the moment it is opened (`gh pr merge <n> --auto --squash --match-head-commit <sha>`); a repository with auto-merge off merges the same way after same-head green. A PR merged on same-head green CI with local proof is Done: the receipt and the move to Done are one step with the merge. A live read-back, deploy check or watch is its own Human UAT item or follow-up ticket and never holds the parent. The hourly stall check (`jira-stalled`) names any LIFE ticket In Progress for 30 minutes (Agent Go for 2 hours) with no change and no `[waiting on]` as its last word.
- **Agent self-promotion (LIFE-742, Jim, Nov 16 2026: "everything but the scary list").** An agent may move a To Do leaf ticket to Agent Go itself (transition ID 17) when it has a Done-when line, every `Blocks` predecessor is Done, and its own text names none of the protected steps: a credential or token (add, move, expose, read), live provider or production access, an Oracle/Mac install or host change, spend beyond the ticket budget, a new table, database or datastore, deleting data, workflow `permissions`, branch protection or other security settings, public ingress. `lifeos.jira.promote.decide(issue)` returns `promote`, `wait` (with the categories) or `skip`; a `skip` changes nothing. `wait` means the ticket stays To Do, the agent posts `[waiting on] Jim: <the one thing>` and adds the label `waiting-on-jim` (removed when Jim answers or the ask is withdrawn, with no second comment restating the answer; the saved filter "Waiting on Jim" lists them, LIFE-753); the code and tests that need none of it may still be built. Each promotion is one comment, `[agent-claude-code] Agent Go: <why it is safe>`. Jim's own moves are unchanged, an agent may promote a ticket it created itself (Jim, Nov 16 2026), and `jim-only` and `hold` stay off limits. New tickets do not say `PLANNING ONLY; leave To Do`: describe protected steps in a `STOP:` line. Jira comments: one receipt at Done, a mid-ticket comment only for `[waiting on] Jim`, and a chat approval is recorded only when it covers a protected step.
- **Auto-release (LIFE-727).** A To Do ticket moves to Agent Go by itself (stage `jira-release`, at most 3 an hour, in rank order) when its parent epic carries the label `auto-release` (Jim's one approval of that epic's list), it has a Done-when line, every Blocks predecessor is Done, it was never in Agent Go before, and it carries none of `jim-only`, `watch`, `hold`, `protected-file`, `needs-approval`, `planning-only`.
- **One page.** AGENTS.md section "Delivery flow v3 — the whole job" is the one-page rules sheet; these parts are the reference.
