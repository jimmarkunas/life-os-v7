### Deterministic agent work selection — mandatory when an authorized execution session starts or resumes

This is a **pull rule**, not a ChatGPT dispatch queue. When an authorized coding agent is invoked, resumes its existing package, or completes a Jim-accepted package, **the agent** selects the next eligible LIFE issue from live Jira. ChatGPT does not routinely nominate an issue or generate a handoff prompt. Instructions alone do not wake an idle Claude/Codex session; use only an existing approved invocation mechanism, never a new scheduler, poller, watchdog or dispatcher. A Jira status change, including release into `Agent Go`, does not by itself start a dormant agent; the queue is what an already-running, authorized agent reads when it starts, resumes or finishes a package.

1. **Resume before selecting.** Fresh-read the current active LIFE issue, attached PR/head and the exact lane claim in Development Projects when concurrent writers are possible. A valid unfinished package is sticky until accepted Done, formally blocked, or explicitly reassigned. Also check for same-lane `acceptance-pending` issues: unresolved live acceptance is a **hold on next-package selection** even when the Jira status remains To Do, until that package is accepted or Jim explicitly reprioritizes the hold. This label never authorizes a diagnostic/live run. Do not abandon an active package merely because another issue appears higher in the backlog.
2. **Select from the Agent Go queue, not documents.** With no valid active package, query live Jira for the human-released queue, then keep only issues in the agent's approved delivery lane: `project = LIFE AND status = "Agent Go" AND issuetype != Epic ORDER BY priority DESC, Rank ASC`. An issue outside `Agent Go` is never selected autonomously, and an agent never promotes work into `Agent Go` to make it selectable. Skip, without any Jira mutation, every candidate with an incomplete incoming `Blocks` predecessor, missing or invalid ownership or lane, an `acceptance-pending` hold (step 1), a conflicting or already-claimed writer, or an execution environment the agent does not support; also skip parked/unapproved products, issues owned by another lane and anything whose authorization provenance cannot be verified. A candidate must still have an owning Epic, a clear product/maintenance authorization (an individual approval, or a child recorded and read back in Jira inside an approved Epic's envelope; creating a child never authorizes it by itself) and a known lane/assignee or explicit approved claim. A `To Do` status or a linked LOS idea alone does not authorize execution.
3. **Order: Priority, then Rank.** Among the eligible candidates take the highest Jira Priority first; Rank breaks ties, including ties at the default Medium. The human releasing the work sets Priority and Rank; agents never reprioritize or reorder issues. Do not substitute historical WBS-row order, issue creation date, alphabetical issue keys or a cached snapshot. If a dependency or ordering contradiction prevents a decision, report it to the Jira planning owner as `QUEUE_NOT_READY` and do not guess.
4. **Preflight and claim.** Re-read the candidate's status, assignee/ownership, incoming blocker links, scope, authorization provenance and required permission scopes just before starting; verify repository/workspace affinity, that no other work is active for this agent and that the exclusive-writer mutation surface is free. Only after the claim succeeds make the supported workflow transition Agent Go to In Progress (ID 6, "Start authorized work"), verify Jira/coordination read-back, then execute the established Jira-first lifecycle. A claimed `In Progress` issue is not proof of an authorized or functioning agent session.
5. **Fail closed, do not dispatch around missing data.** If Jira access, authorization, lane assignment, product readiness, ordering or predecessor completion cannot be established, report `QUEUE_NOT_READY — <exact issue/field or access gap>` and stop automatic selection. Surface the Jira planning correction for the owning product/Tech Lead; do not ask ChatGPT to choose an arbitrary next ticket, invent a priority, copy a new backlog, or silently substitute a cached snapshot. When there is genuinely no eligible ticket, including an empty `Agent Go` queue, report `NO_ELIGIBLE_WORK` without mutation; do not fall back to pulling from `To Do`.
6. **Completion remains gated.** PR/CI success is `LANDED`, not Done. After the applicable proof and Jim's final acceptance—or evidence-based closeout that the issue delegated in advance under §3 Bounded autonomy—the authorized Jira owner transitions the LIFE issue to Done and reads it back. Only at that verified completion boundary may the same authorized, correctly anchored execution session repeat this selection rule.

**Queue readiness requirement:** Jira must actually contain usable lane ownership, curated delivery order/priority, truthful statuses, and issue-level dependency/approval evidence. Merely documenting this selector does not make an unassigned or unprioritized Jira board autonomously executable. Review and repair planning data **in Jira**, without creating another source of truth; do not silently mass-assign or reorder work as part of a development session.

**Approved initial Jira lane-label convention (October 13):** Native LIFE issue labels `lane-career-v7` and `lane-edge-comm` identify the two existing authorized lanes; `pull-ready` is retired as an execution selector: it is not required, does not release or authorize work, and is ignored where it still appears (it never bypasses live blockers, product acceptance, workspace affinity, or the single V7 repo-heavy writer). Each authorized session first resumes its own valid In Progress package, then selects from the `Agent Go` queue in its own lane as defined above. A candidate with a non-Done incoming `Blocks` predecessor is not eligible; a reviewed next task becomes eligible only after the predecessor's approved Done read-back. Ordering is Jira Priority, then Rank; return `QUEUE_NOT_READY` only when the lane, owner, dependency or queue data needed to decide is missing. Do not infer lane from unassigned human Jira assignee, old WBS owner text, or generic Medium priority. Only the Jira planning owner authorizes applying/changing these labels, with one delegation: the approved lead of a specifically authorized finite Epic acts as delegated Jira planning owner solely for newly created, in-scope children of that Epic, and may set their lane, owner, dependencies, Priority and Rank as the approved Epic plan requires, verified by Jira read-back before execution. The delegation never lets an agent release work into `Agent Go`, which stays a human release, and does not reach any other ticket: agents must not reprioritize, relabel, reorder or reassign unrelated issues, and it never overrides blockers, product acceptance, workspace affinity or the single-writer claim. The selector does not awaken idle external coding agents or grant Jira credentials.

### Jira-first development lifecycle — mandatory across ChatGPT, Claude Code, Codex and approved Edge implementers

1. **Intake and product decision.** Use the current LOS idea for new product outcomes and priorities; move a reviewed idea out of Parking lot only after Jim's approved prioritization. Implementation bugs and maintenance can start directly as LIFE issues under the owning Epic. Reuse an existing issue before creating one; never create a parallel planning record to keep work moving.
2. **Retrieve the exact live LIFE issue before accepting work.** Inspect its key, parent Epic, current status, blocker/dependency links, scope, acceptance boundary and WBS ID, plus the linked LOS idea where relevant. Read the owning Notion product canon and only the directly applicable technical contracts. The frozen V7 roadmap cannot resolve current priority or state. No ticket or ambiguous scope: the authorized Jira owner must first reconcile/create the narrow issue; do not invent an implementation commitment.
3. **Check ownership only when overlap is plausible.** Fresh-read Notion Development Projects for current concurrency/claim facts and preserve one repo-heavy writer per V7 mutation surface. The authorized Jira owner may set LIFE In Progress when execution actually starts, with direct read-back; do not change status or claim ownership merely from a prompt or a branch name.
4. **Implement in the approved workspace.** Follow this Policy's workspace, scope, architecture, permission and proof gates. Include the actual LIFE key in PR/title/commit references (branch and PR title format: **LIFE Jira issue-writing contract**), retain the stable WBS ID, and preserve relevant LOS delivery links. One bounded branch/PR per coherent package; do not simultaneously mutate another owner's work.
5. **Report truthful milestones.** `LANDED` requires the intended PR and targeted proof, not Done. For runtime-facing work require same-head CI, the production-shaped pre-merge gate, and then live authoritative acceptance as applicable. Set or request meaningful LIFE blocker/in-progress/acceptance updates only from verified evidence; never auto-complete a ticket because CI or a PR is green.
6. **Accept and close.** Once required real-boundary evidence is verified and Jim's final Done approval is obtained—or evidence-based closeout delegated in advance by the issue under §3 Bounded autonomy—transition the LIFE issue to Done and read it back. Preserve LOS idea-to-delivery links and update product stage only when supported by actual approved product state; no unrelated issue/idea changes.
7. **Unavailable Jira/tool access.** Independent next-task selection requires authorized fresh Jira access. A verified exact-issue handoff from the ChatGPT/Tech Lead may support a *specifically authorized one-off implementation*, but cannot substitute for autonomous queue selection. Such a handoff is evidence for that bounded code package, **not** a claim of live Jira access or permission to mutate Jira. If fresh scope/dependency/owner state cannot be established, fail closed for the affected execution or write and report the specific unavailable gate. Do not fall back to GitHub/Notion status snapshots or add a sync service.

### Requirement-change reconciliation — Jim-approved November 1, 2026 (LIFE-79)

This is an event-driven duty of the owning ChatGPT/Jira planning agent, not a scheduler, audit, backlog, workflow, status, automation or approval gate. When Jim approves a change to a product requirement or execution architecture, the change is not complete until the directly affected **current** LIFE/LOS records are reconciled in the same bounded change, so a fresh agent following normal links meets no contradictory active instruction.

1. **Decision first.** Record the deciding human, date/source, owning LOS/Notion requirement and the exact new invariant; never infer approval from assistant-written text or an old ticket, and keep working hypotheses distinct from decisions.
2. **Bounded impact search.** Read the changed issue, its Epic and children, live native `Blocks`/`Depends` links and direct related LOS issues, then run one bounded text search for the superseded requirement, tool or obsolete key in non-Done LIFE/LOS records and inspect only plausible live consumers. Do not scan unrelated history.
3. **Correct in place.** Replace superseded directions in the operative summary, description, acceptance criteria and prerequisites of affected open issues rather than prepending a note above contradictory commands. Update native links that are no longer valid; remove a link only when no true technical dependency remains and the owner approved that specific removal. A retired tool or plan must not remain an active prerequisite, step, selected integration, queue or authorization route. Change status of retired active work only on a documented owner disposition.
4. **Preserve.** Keep comments, changelog, completed evidence, statuses, unrelated scope, priority, owners, approvals, permissions and protected or production work unchanged. Historical or Cancelled records may be cited only as `HISTORICAL — SUPERSEDED`, never as current authority; current records link the controlling LOS decision and Notion canon.
5. **Read back.** Re-fetch every changed issue, its links and the relevant search, confirm no contradictory live instruction remains in the affected graph, and record one receipt in the owning issue (decision/source, keys, fields and links changed, history kept, revisions verified, exceptions). Report `RECONCILED` only then; an unsafe link or missing canon is reported as `PARTIAL / BLOCKED` with the exact keys, owner and next action.

Reconciliation never moves an issue into `Agent Go` or starts an agent; Agent Go release, Priority order, claims, one-writer scope and protected-operation gates are unchanged.
