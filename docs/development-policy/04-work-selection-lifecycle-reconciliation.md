### Deterministic agent work selection — mandatory when an authorized execution session starts or resumes

This is a **pull rule**, not a ChatGPT dispatch queue. When an authorized coding agent is invoked, resumes its package or finishes a Jim-accepted one, **the agent** picks the next eligible LIFE issue from live Jira. ChatGPT does not nominate issues or write handoff prompts. Instructions alone do not wake an idle session, and a Jira status change (including release to `Agent Go`) does not by itself start a dormant agent: use only an existing approved invocation, never a new scheduler, poller, watchdog or dispatcher.

1. **Resume first.** Fresh-read your active LIFE issue, its PR/head and, where writers may collide, your lane claim in Development Projects. An unfinished package is sticky until accepted Done, formally blocked or reassigned.
2. **Select from the Agent Go queue, not documents.** `project = LIFE AND status = "Agent Go" AND issuetype != Epic ORDER BY priority DESC, Rank ASC`, in your lane. Nothing outside Agent Go is selected autonomously and an agent never promotes work into `Agent Go`. Skip, without any Jira change, issues with an incomplete incoming `Blocks` predecessor, missing or invalid owner or lane, a conflicting or already-claimed writer, an execution environment the agent does not support, a parked or unapproved product, another lane, or unverifiable authorization. A candidate needs an owning Epic, clear authorization (an individual approval, or a child recorded and read back inside an approved Epic's envelope) and a known lane. `To Do` or a linked LOS idea authorizes nothing. Release leaf issues only; an issue with children is a container.
3. **Order is Priority, then Rank.** Rank breaks ties, including at the default Medium. Humans set both; agents never reprioritize or reorder. No WBS order, creation date, key order or cached snapshot. A contradiction → `QUEUE_NOT_READY`.
4. **Start.** Re-read status, blockers and scope; keep one writer per mutation surface (Concord `start_work`/`finish_work` are optional, never a refusal). Make the supported transition Agent Go to In Progress (ID 14, "Start work (authorization receipt required)"), verify the read-back, then run the lifecycle below. Moving a ticket to Agent Go IS Jim's approval.
5. **Fail closed.** If access, authorization, lane, readiness, order or predecessors cannot be established report `QUEUE_NOT_READY — <exact gap>` and stop; do not ask ChatGPT to pick, invent a priority or use a snapshot. An empty `Agent Go` queue is `NO_ELIGIBLE_WORK` with no mutation and no pull from To Do.
6. **Completion.** PR/CI success is `LANDED`. After merge, receipt and read-back, the implementing agent moves the issue to Done (delegated closeout is the default); Jim reopens it or files a Bug. Then the same session repeats selection.

**Queue readiness.** Jira must hold usable lane ownership, curated order, truthful statuses and issue-level dependency and approval evidence; documenting this selector does not make a board executable. Repair planning data in Jira without creating another source of truth, and never mass-assign or reorder inside a development session.

**Lane labels (October 13).** `lane-career-v7` and `lane-edge-comm` identify the two authorized lanes; the lane label is the routing and ownership field and the assignee may stay Jim (agents are not Jira users). Only the Jira planning owner applies or changes lane labels, with one delegation: the approved lead of a specifically authorized finite Epic acts as planning owner solely for new, in-scope children of that Epic (lane, owner, dependencies, Priority, Rank), verified by read-back before execution. It never lets an agent release into `Agent Go`, never reaches other tickets and never overrides blockers, acceptance, affinity or the one-writer claim.

**Release simplification — Jim-approved November 4, 2026.** (1) Jim's authenticated instruction naming the issue and scope starts that work without an Agent Go release; `authorization.provenance` records channel and time. (2) A whole `Blocks` chain may be released in one bulk transition; the links and this selector sequence it. (3) Readiness minimum: a valid key, at least one Done-when line (a Given/When/Then row or a bullet under "Done when") and every `Blocks` predecessor Done; everything else is a `warn` line (`python -m lifeos.readiness`). (4) For an Epic Jim approved with a written non-protected scope, its approved lead may release in-scope children it creates into Agent Go; protected steps stay owned human Sub-tasks that block the work. This is the only relaxation of "agents never promote"; strike it to keep human-only release.

**Scoping.** One planning pass per Epic: write executable Tasks with Given/When/Then, a fast-proof command, `Blocks` links and protected-operation permissions, run the readiness validator on each, turn every gap into a fix or an owned human Sub-task, then stop; approved scope is not re-litigated.

### Jira-first development lifecycle — mandatory across ChatGPT, Claude Code, Codex and approved Edge implementers

1. **Intake.** New product outcomes come from the current LOS idea (moved out of Parking lot only on Jim's prioritization); bugs and maintenance start directly as LIFE issues under the owning Epic. Reuse an existing issue; never create a parallel planning record.
2. **Read the live issue before accepting work:** key, parent Epic, status, blockers, scope, acceptance boundary, WBS ID and linked LOS idea, plus the owning Notion canon and only the technical contracts that apply. The frozen roadmap cannot settle priority or state. No ticket or ambiguous scope: the Jira owner reconciles or creates the narrow issue first.
3. **Ownership.** Read Development Projects only where overlap is plausible; keep one repo-heavy writer per mutation surface. Set In Progress only when execution actually starts, with read-back; never from a prompt or branch name alone.
4. **Implement** in the approved workspace within this policy's scope, architecture, permission and proof gates. Put the LIFE key in the branch, PR title and commits (format: the issue-writing contract), keep the WBS ID and LOS links, one bounded branch and PR per package.
5. **Report truthfully.** A ticket is Done when its PR is merged on same-head green CI with local proof. Live acceptance is a watch, never a gate. Update Jira only from verified evidence.
6. **Close.** After merge, receipt and read-back the implementing agent moves the issue to Done (delegated closeout is the default for every non-protected ticket); Jim reopens it or files a Bug. Update product stage only to match real approved state.
7. **Jira unavailable.** Autonomous selection needs fresh Jira access. A verified exact-issue handoff supports one specifically authorized implementation but is not live Jira access or permission to mutate Jira; if scope, dependency or owner state cannot be established, fail closed for that action and name the gate. No GitHub or Notion status snapshot, no sync service.

**Delivery flow v3 — Jim-approved November 9, 2026.**
- **One ticket, one approval.** Moving a ticket to Agent Go is the approval and covers everything inside the written scope. A change of plan is an edit to the ticket plus one line `Scope change: <what> — Jim, <time CT>`; the description beats comments. A scoping note is one page (at most 2,000 characters: Outcome, 3 to 5 Done-when checks, Not in scope); one execution ticket is one PR or one sheet edit.
- **One receipt.** After merge post one comment: PR link, what changed, how it was verified, what is unverified. The agent moves the ticket to Done. Label `needs-uat` means stop at Human UAT with exact steps for Jim (new user-facing UI or judgment only).
- **Ticket truth.** The claiming agent edits its ticket in the same session that reality changes; a superseded ticket is Cancelled with a line naming its replacement.
- **Transitions.** Any status can reach any status so agents are never stuck. To Do and Agent Go reach In Progress only through ID 14; every other status uses "Resume work".
