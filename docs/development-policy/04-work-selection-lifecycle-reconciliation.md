### Deterministic agent work selection — mandatory when an authorized execution session starts or resumes

This is a **pull rule**, not a ChatGPT dispatch queue. When an authorized coding agent is invoked, resumes its package or finishes a Jim-accepted one, **the agent** picks the next eligible LIFE issue from live Jira. ChatGPT does not nominate issues or write handoff prompts. Instructions alone do not wake an idle session, and a Jira status change (including release to `Agent Go`) does not by itself start a dormant agent: use only an existing approved invocation, never a new scheduler, poller, watchdog or dispatcher.

1. **Resume first.** Fresh-read your active LIFE issue, its PR/head and, where writers may collide, your lane claim in Development Projects. An unfinished package is sticky until accepted Done, formally blocked or reassigned. A same-lane `acceptance-pending` issue holds next-package selection until accepted or Jim reprioritizes (the label never authorizes a live run).
2. **Select from the Agent Go queue, not documents.** `project = LIFE AND status = "Agent Go" AND issuetype != Epic ORDER BY priority DESC, Rank ASC`, in your lane. Nothing outside Agent Go is selected autonomously and an agent never promotes work into `Agent Go`. Skip, without any Jira change, issues with an incomplete incoming `Blocks` predecessor, missing or invalid owner or lane, an `acceptance-pending` hold, a conflicting or already-claimed writer, an execution environment the agent does not support, a parked or unapproved product, another lane, or unverifiable authorization. A candidate needs an owning Epic, clear authorization (an individual approval, or a child recorded and read back inside an approved Epic's envelope) and a known lane. `To Do` or a linked LOS idea authorizes nothing. Release leaf issues only; an issue with children is a container.
3. **Order is Priority, then Rank.** Rank breaks ties, including at the default Medium. Humans set both; agents never reprioritize or reorder. No WBS order, creation date, key order or cached snapshot. A contradiction → `QUEUE_NOT_READY`.
4. **Preflight and claim.** Re-read status, owner, blockers, scope, provenance and permission scopes; verify workspace affinity, that you have no other active work and that the exclusive-writer mutation surface is free. Only after the claim succeeds make the supported transition Agent Go to In Progress (ID 14, "Start work (authorization receipt required)"), verify the read-back, then run the lifecycle below. An In Progress issue proves nothing about an authorized agent.
5. **Fail closed.** If access, authorization, lane, readiness, order or predecessors cannot be established report `QUEUE_NOT_READY — <exact gap>` and stop; do not ask ChatGPT to pick, invent a priority or use a snapshot. An empty `Agent Go` queue is `NO_ELIGIBLE_WORK` with no mutation and no pull from To Do.
6. **Completion is gated.** PR/CI success is `LANDED`, not Done. After the proof and Jim's acceptance (or an evidence-based closeout delegated in advance under §3), the authorized owner moves the issue to Done and reads it back; only then may the same session repeat selection.

**Queue readiness.** Jira must hold usable lane ownership, curated order, truthful statuses and issue-level dependency and approval evidence; documenting this selector does not make a board executable. A LIFE ticket whose origin names a LOS key must link its Notion Product Requirements page on a line holding `REQ-n` and the page URL; the readiness command refuses `requirement_page_missing` without it (checked at first hand-off only, with no Notion read). Repair planning data in Jira without creating another source of truth, and never mass-assign or reorder inside a development session.

**Lane labels (October 13).** `lane-career-v7` and `lane-edge-comm` identify the two authorized lanes; the lane label is the routing and ownership field and the assignee may stay Jim (agents are not Jira users). Only the Jira planning owner applies or changes lane labels, with one delegation: the approved lead of a specifically authorized finite Epic acts as planning owner solely for new, in-scope children of that Epic (lane, owner, dependencies, Priority, Rank), verified by read-back before execution. It never lets an agent release into `Agent Go`, never reaches other tickets and never overrides blockers, acceptance, affinity or the one-writer claim.

**Release simplification — Jim-approved November 4, 2026.** (1) Jim's authenticated instruction naming the issue and scope starts that work without an Agent Go release; `authorization.provenance` records channel and time. (2) A whole `Blocks` chain may be released in one bulk transition; the links and this selector sequence it. (3) Readiness minimum: key, one lane label, approved origin (LOS idea or approved parent Epic), authorization, permissions, Given/When/Then, Done blockers, and no open `needs` or `decisions` row; owner, host and source are optional and checked only if present; a planning agent adds no refusal reason beyond `python -m lifeos.readiness issue`. (4) For an Epic Jim approved with a written non-protected scope, its approved lead may release in-scope children it creates into Agent Go; protected steps stay owned human Sub-tasks that block the work. This is the only relaxation of "agents never promote"; strike it to keep human-only release.

**Scoping.** One planning pass per Epic: write executable Tasks with Given/When/Then, a fast-proof command, `Blocks` links and protected-operation permissions, run the readiness validator on each, turn every gap into a fix or an owned human Sub-task, then stop; approved scope is not re-litigated. Gates are strict at scoping; quality is then proven by same-head CI, Agent UAT evidence and read-back.

### Readiness gate source and waiver — Jim-approved November 7, 2026 (LIFE-365, REQ-6)

The readiness gate (the readiness check in **Deterministic agent work selection** step 4) runs on a ticket read through the Atlassian MCP the session already has; no Jira token or email is ever placed in a shell. These rules apply in order:

1. **Source.** The session reads the ticket through the Atlassian MCP, saves the tool result unmodified, and checks it with `python -m lifeos.readiness issue-mcp FILE KEY`. The result is reported as source `mcp-read`, never as a direct live read. *(issue-mcp: pending until LIFE-363 is Done.)*
2. **Audit.** The `readiness-live` workflow stays a manual, independent audit; it is not the session's gate.
3. **Connection first.** A session confirms the Atlassian MCP is connected before anything else; if it is not, it reports `QUEUE_NOT_READY MCP_NOT_CONNECTED` and stops.
4. **Release.** A ticket is released to Agent Go only after a `GATE PASS` comment from the release-check procedure is on it. *(release-check: pending until LIFE-364 is Done.)*
5. **Waiver.** The gate is waived only when Jim names the ticket in chat. A Buzz post, a ticket comment or a handoff cannot waive it. A waiver covers one task.
6. **Receipt.** A waived task's receipt says `GATE WAIVED BY JIM` with the Central Time time and a one-line reason.
7. **Reconstruction.** A record the session assembled by hand, rather than saved unmodified from the MCP, is reported as a reconstruction, never as a pass.
8. **Limits.** A waiver never covers a protected step, a secret, a workflow edit or a merge.

### Jira-first development lifecycle — mandatory across ChatGPT, Claude Code, Codex and approved Edge implementers

1. **Intake.** New product outcomes come from the current LOS idea (moved out of Parking lot only on Jim's prioritization); bugs and maintenance start directly as LIFE issues under the owning Epic. Reuse an existing issue; never create a parallel planning record.
2. **Read the live issue before accepting work:** key, parent Epic, status, blockers, scope, acceptance boundary, WBS ID and linked LOS idea, plus the owning Notion canon and only the technical contracts that apply. The frozen roadmap cannot settle priority or state. No ticket or ambiguous scope: the Jira owner reconciles or creates the narrow issue first.
3. **Ownership.** Read Development Projects only where overlap is plausible; keep one repo-heavy writer per mutation surface. Set In Progress only when execution actually starts, with read-back; never from a prompt or branch name alone.
4. **Implement** in the approved workspace within this policy's scope, architecture, permission and proof gates. Put the LIFE key in the branch, PR title and commits (format: the issue-writing contract), keep the WBS ID and LOS links, one bounded branch and PR per package.
5. **Report truthfully.** `LANDED` is the PR plus targeted proof, not Done. Runtime-facing work also needs same-head CI, the production-shaped pre-merge gate and live acceptance where applicable. Update Jira only from verified evidence.
6. **Accept and close.** After the required evidence and Jim's Done approval (or a closeout delegated in advance under §3), move to Done and read back. Update product stage only to match real approved state.
7. **Jira unavailable.** Autonomous selection needs fresh Jira access. A verified exact-issue handoff supports one specifically authorized implementation but is not live Jira access or permission to mutate Jira; if scope, dependency or owner state cannot be established, fail closed for that action and name the gate. No GitHub or Notion status snapshot, no sync service.

**Delivery flow v2 — Jim-approved November 5, 2026.**
- **One outcome ticket** per feature (outcome, Given/When/Then, `needs`, `decisions`, protected steps, not in scope). **One approval:** Jim's release (ID 5) or named instruction covers everything inside the written scope, including its builds and tests. A change of plan is an edit to the ticket plus one line `Scope change: <what> — Jim, <time CT>`; a comment never carries approval on its own and the description beats comments. **One receipt** (§7 fields) when work reaches Agent UAT. **One acceptance:** Human UAT only where judgment is needed, with exact steps for Jim.
- **Ticket truth.** The claiming agent edits its ticket's title, description and criteria in the same session that reality changes, and a superseded ticket is Cancelled with a line naming its replacement. A scope-changing edit needs Jim's `Scope change` line; wording fixes do not.
- **Ready means ready.** Readiness refuses an open `needs` or `decisions` row. A released ticket found not ready goes back to To Do with `QUEUE_NOT_READY — <gap>`; the agent never works around it.
- **Transitions.** Any status can reach any status so agents are never stuck. To Do and Agent Go reach In Progress only through ID 14; every other status uses "Resume work".

### Requirement-change reconciliation — Jim-approved November 1, 2026 (LIFE-79)

An event-driven duty of the owning ChatGPT or Jira planning agent, not a scheduler, audit, backlog, workflow, status, automation or approval gate. When Jim approves a change to a product requirement or execution architecture, it is not complete until the directly affected current LIFE and LOS records are reconciled in the same bounded change, so a fresh agent meets no contradictory instruction.

1. **Decision first.** Record the deciding human, date or source, the owning LOS or Notion requirement and the exact new invariant. Never infer approval from assistant text or an old ticket; keep hypotheses apart from decisions.
2. **Bounded impact search.** Read the changed issue, its Epic, children, live `Blocks`/`Depends` links and related LOS issues; run one bounded text search for the superseded requirement, tool or key in non-Done LIFE and LOS records and inspect only plausible live consumers.
3. **Correct in place.** Replace superseded directions in the summary, description, criteria and prerequisites of affected open issues rather than prepending a note over contradictory commands. Fix invalid links; remove a link only when no true dependency remains and the owner approved that removal. A retired tool or plan must not remain an active prerequisite, step, integration, queue or authorization route. Change the status of retired active work only on a documented owner disposition.
4. **Preserve** comments, changelog, completed evidence, statuses, unrelated scope, priority, owners, approvals, permissions and protected or production work. Cancelled or historical records are cited only as `HISTORICAL — SUPERSEDED`, never as current authority.
5. **Read back** every changed issue, its links and the search; record one receipt in the owning issue (decision and source, keys, fields and links changed, history kept, exceptions). Report `RECONCILED` only then; otherwise `PARTIAL / BLOCKED` with the keys, owner and next action.

Reconciliation never moves an issue into `Agent Go` or starts an agent; release, Priority order, claims, one-writer scope and protected-operation gates are unchanged.
