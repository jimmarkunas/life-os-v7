### LIFE Jira issue-writing contract — Jim-approved October 29, 2026 (LIFE-79)

Every LIFE issue written or materially edited after this policy merges follows this contract. The machine-readable field list is [`docs/jira/issue-schema.v1.json`](../jira/issue-schema.v1.json); the Notion **Jira Ticket Writing Guide** is the concise human companion, never a second policy. When they differ, this section and the schema win.

- **Statement.** A Story starts with one user story: `As a [specific user/persona], I want [capability], so that [benefit].` Name the real user when known. A Task or Bug that does not fit a user story uses one bounded outcome statement: what will exist, for whom, and where it ends.
- **Acceptance criteria stay separate from the statement.** Write each criterion as `Given [precondition], when [action or event], then [observable result].` Write one criterion per distinct behavior, edge case or required UI state.
- **System of record.** Jira stays the execution and acceptance record. Link the exact Notion requirement; do not copy the full requirement into Jira (§1 planning authority).
- **Execution setup.** Each issue records its tools and their purpose, the execution host, its setup state (`ready`, `not_required`, or a named prerequisite issue) and its owner. Reference secrets only by identifier (Bitwarden item or project, GitHub Actions secret or variable name, Oracle service name). Never put a secret value in Jira.
- **Human actions.** A human action that blocks the work (a decision, access, an input or setup) is an owned sub-task. It names the owner, the exact action and an explicit unblock condition, and the blocked work links to it.
- **UI and Figma.** Classify the UI scope as in the UI-first applicability gate above. For new or changed UI, link the applicable Figma file and frames, or state why none applies, and follow that gate unchanged.
- **Agent UAT and Human UAT statuses.** LIFE uses the `Agent UAT` and `Human UAT` workflow statuses. Every issue must pass Agent UAT before Done: verify each acceptance criterion against the exact branch and SHA, run the fast proof, check relevant negative/error cases, and record the evidence on the issue. Human UAT is required only when human judgment is needed (user-facing flow, visual design, data interpretation, or stakeholder judgment); otherwise record why it is not required. When required, the issue moves through Human UAT and records the named human's acceptance evidence before Done. These statuses do not create separate QA layers.
- **Fast proof first.** Each issue names a schedule-independent fast proof: a deterministic fixture or clock test, or an on-demand run through the real entrypoint, with read-back. A scheduled production run is never the first test. Any later live acceptance step stays separate, owned and authorized under the existing gates.
- **Evidence and receipt.** Record the exact PR, validated head SHA, required proof and any applicable review or exception on the issue, and close with a concise completion receipt. A merged PR alone is not product Done; the final-acceptance rules in §1 and §7 are unchanged.
- **Authorization, scope, assignment, and routing.** Jim's explicit, identifiable, authenticated instruction or approval, given to an agent in ChatGPT, Claude, Codex or Buzz, is valid execution authorization for its stated scope and does not have to be repeated in Jira; it must identify the approved issue or Epic, scope and permitted execution. The `Agent Go` status is the explicit, human-released queue for autonomous agent execution: Jim, or a named human planning owner he has specifically delegated in Jira, releases scoped, approved work into it with the existing Jira transition ID 5 (To Do to Agent Go, "Authorize agent work"). Jira restricts that transition to the existing `org-admins` group, which currently contains only Jim. That restriction is **not** an agent-identity boundary: an agent acting through Jim's authenticated Jira connector can technically invoke it, so the rule that **an agent never promotes its own, a self-created or any unapproved issue into Agent Go** is an operational policy gate and not a technical guarantee. A status change alone starts nothing: `Agent Go` does not wake a dormant agent, grant credentials or replace the checks below. No separate `AGENT-AUTH` comment is required. A connector-written or agent-written Jira comment (which a shared credential may attribute to Jim) may record that instruction but is not an additional approval gate and, by itself, is not proof of approval; agents never invent, infer or expand an approval. For an asynchronous handoff the receiving agent retains the source attribution (channel, issuer, time) and the exact scope, and if the underlying human authorization genuinely cannot be established or its scope verified, execution fails closed. Protected actions retain their separate permission requirements. A person, assisted by an agent or chat, defines the work in Jira. Authorization covers the approved issue and its explicitly approved in-scope subtasks. Jim's explicit, authenticated approval of a named, finite feature Epic (exact Jira key and approved outcome, acceptance criteria and product boundaries) additionally authorizes that Epic's assigned lead and approved agents to create and execute the necessary in-scope child Tasks/Sub-tasks without a further human approval per child, provided each child is created under that Epic with the required metadata, recorded and read back in Jira before execution, and passes every eligibility check in this bullet and in Deterministic agent work selection (dependencies, human prerequisites, lane owner, single-writer claim, isolated worktree, required CI and human UAT). Creating a child never places it in Agent Go; only a human release does, and an agent never releases work it created, leads or will execute. The Epic envelope never covers a new product outcome, architectural override, another Epic or project, client data, or any secret, spending, permission, production or other protected action, which keep their own gates, and it is never inferred from an Epic's existence, status, label or an agent-written comment; the dormant Agent Go inheritance Automation is not an approval mechanism. Work taken from the Agent Go queue starts with the existing Jira transition ID 6 (Agent Go to In Progress, "Start authorized work") only after a successful claim and every other eligibility check pass. Work Jim directs by an explicit, named instruction or inside an approved Epic envelope, and which was therefore never released into Agent Go, starts with transition ID 14 (To Do to In Progress, "Start work (authorization receipt required)") under the same checks; the name refers to existing verifiable approval evidence, not a new comment. Before starting, the agent checks the live issue, prerequisites, incoming blockers, lane, authorization provenance, permission scopes, active session, single-writer claim and permitted operations. The transition is not a security boundary; real limits stay with agent invocation, credentials, repository permissions and protected-action gates. It does not authorize out-of-scope work or changes to another project; obtain separate authorization for BAD/BPP work. Every actionable issue has an explicit lane and agent owner. Agents resume their own active issue first, then select eligible work from the Agent Go queue in their lane by Jira Priority (highest first) with Rank as the tie-breaker; they do not compete across lanes, self-assign unowned work or promote work into Agent Go. Only independent issues/subtasks may run in parallel; an issue waits until every incoming `Blocks` predecessor is Done. Lane labels (`lane-career-v7`, `lane-edge-comm`) route work only; `pull-ready` is no longer an execution selector and never authorizes execution. Once authorized and started, the assigned agent may implement, open a PR, and merge a routine authorized change once all required same-head checks and relevant proof pass, provided their GitHub permissions and the repository's actual protection rules permit the merge. An external independent technical review is not a universal prerequisite. Non-production deployment remains subject to existing agent and environment permissions; Authorization does not override native GitHub approval requirements or protected-action permissions. Production access/writes, secret access, spending, and permission changes remain governed by existing per-agent, project, and environment controls; never expose secret values. If policy conflicts with live Jira or repository configuration, stop, report the conflict, and await reconciliation.
- **Branch and PR names.** Code branch: `<project-key-lower>/<ISSUE-KEY>/<fix-version-slug>/<component-slug>/<scope-slug>`, for example `life/LIFE-79/platform-core-os-1-0-0/platform-core-os/jira-issue-contract`. PR title: `[<ISSUE-KEY>][<component-slug>][<fix-version-slug>] <outcome>`. A slug is the Jira name lower-cased with each run of other characters replaced by one `-`. The PR body links the Jira issue and records its acceptance criteria, the validated head SHA, the proof, any actually required review and exceptions.

The UI-first, privacy, dependency, release, single-writer and final-acceptance rules in this policy are unchanged. If a required field cannot be filled from authoritative evidence, the issue is not ready: name the missing field for its owner (`QUEUE_NOT_READY`).
