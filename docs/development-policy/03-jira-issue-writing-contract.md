### LIFE Jira issue-writing contract — Jim-approved October 29, 2026 (LIFE-79)

Every LIFE issue written or materially edited follows this contract. The field list is [`docs/jira/issue-schema.v1.json`](../jira/issue-schema.v1.json); the Notion **Jira Ticket Writing Guide** is a human companion, never a second policy. This section and the schema win over it.

- **Statement.** A Story: `As a [specific user], I want [capability], so that [benefit].` A Task or Bug: one bounded outcome (what will exist, for whom, where it ends).
- **Acceptance** is separate from the statement: one `Given [precondition], when [action], then [observable result].` per behavior, edge case or required UI state.
- **Record.** Jira is the execution and acceptance record; link the exact Notion requirement, do not copy it. Reference secrets by identifier only; never put a value in Jira.
- **Setup.** Tools and their purpose, execution host, setup state (`ready`, `not_required` or a prerequisite issue), owner.
- **UI.** Classify UI scope per the UI-first gate; for new or changed UI link the Figma frames or state why none apply.
- **UAT.** LIFE keeps the `Agent UAT` and `Human UAT` workflow statuses. Human UAT only with the label `needs-uat` (new user-facing UI or anything judgment-based): stop there with exact steps for Jim and record his acceptance. Otherwise the same-head CI, fast proof and read-back in the receipt are the proof and the agent moves the issue to Done.
- **Fast proof first.** A deterministic fixture or clock test, or an on-demand run through the real entrypoint with read-back. A scheduled production run is never the first test; later live acceptance stays separate, owned and authorized.
- **Receipt.** One comment on completion: PR link, what changed, how it was verified, what is unverified. The agent then moves the issue to Done; Jim reopens it or files a Bug.
- **Authorization, scope, assignment, and routing.**
  1. Jim's explicit, identifiable, authenticated instruction (ChatGPT, Claude, Codex or Buzz) naming the issue or Epic and scope authorizes it and need not be repeated in Jira. A connector- or agent-written comment may record it but is not proof; agents never invent, infer or widen an approval. An asynchronous handoff keeps its source (channel, issuer, time) and exact scope; if the authorization or scope cannot be verified, fail closed.
  2. `Agent Go` is the human-released queue for unattended pulls. Jim, or a named human planner he delegated in Jira, releases scoped, approved work with transition ID 5 (To Do to Agent Go, "Authorize agent work"). Its `org-admins` restriction is not an agent-identity boundary (an agent using Jim's connector can invoke it), so the rule that **an agent never promotes its own, a self-created or any unapproved issue into Agent Go** is an operational policy gate, not a technical guarantee. A status change starts nothing: it wakes no agent, grants no credential and replaces no check.
  3. **Epic envelope.** Jim's approval of a named, finite feature Epic (key, outcome, criteria, boundaries) lets its lead and approved agents create and run the necessary in-scope children without a per-child approval, if each is created under the Epic with the required metadata, read back in Jira before execution, and passes every eligibility check here and in work selection. Creating a child never releases it; an agent never releases work it created, leads or will execute. The envelope never covers a new product outcome, architectural override, another Epic or project, client data, or any secret, spending, permission, production or other protected action, and is never inferred from an Epic's existence, status, label or an agent comment.
  4. **Start.** Agent Go work starts with transition ID 14 ("Start work (authorization receipt required)") after a successful claim and every eligibility check; work Jim names, or inside an Epic envelope, that was never in Agent Go starts with ID 14 from To Do. Work returning from blocked, UAT, Done or Cancelled uses "Resume work". Eligibility: live issue, prerequisites, incoming blockers, lane, authorization provenance, permission scopes, active session, one-writer claim, permitted operations. The transition is not a security boundary; the limits are agent invocation, credentials, repository permissions and protected-action gates. It never authorizes out-of-scope work or another project (BAD/BPP need their own authorization).
  5. **Lanes and order.** Every actionable issue has a lane and an agent owner. Agents resume their own active issue, then take Agent Go work in their lane by Priority (highest first), Rank breaking ties; they never compete across lanes, self-assign unowned work or promote work. Only independent issues run in parallel; an issue waits until every incoming `Blocks` predecessor is Done. Lane labels (`lane-career-v7`, `lane-edge-comm`) route only; `pull-ready` is retired.
  6. **Landing.** The assigned agent may implement, open a PR and merge a routine change once all required same-head checks and relevant proof pass and the repository's rules permit (Part 07 items 3 and 3a); an external independent review is not a universal prerequisite. Non-production deployment follows existing agent and environment permissions. Native GitHub approvals, protected actions, production access or writes, secret access, spending and permission changes keep their own controls; never expose a secret value. If this policy conflicts with live Jira or repository configuration, stop, report and await reconciliation.
- **Branch and PR names.** Branch: `life/LIFE-nnn/<slug>`. PR title: `[LIFE-nnn] <outcome>`. The PR body links the Jira issue and records its criteria, the validated head SHA, the proof and any exceptions.

The UI-first, privacy, dependency, release, single-writer and final-acceptance rules are unchanged. A missing Done-when line or an unfinished `Blocks` predecessor means the issue is not ready (`QUEUE_NOT_READY`); other gaps are warnings.
