# Central authorization gate (LIFE-811 / F02) — synthetic only

`lifeos/platform/authorization_gate.py` is one pure function, `execute`, in front of one side effect. It reuses `capability_catalog.resolve` (LIFE-810), `access_policy.decide` (LIFE-374/403) and a grant shaped like LIFE-707/721's. It adds no service, store, credential or endpoint.

Order: validate, tenant (personal, bytalos, tgp; a caller may exclude one), trusted session, catalog row, policy level, grant (principal, tenant, account, tool), revoke, expiry, purpose, exact action, human approval for send, delete, permission and production, receipt, then the effect. Every deny is before the effect and writes a redacted receipt (fixed words, fingerprints, Central time). No receipt, no effect.

Approvals are one request each, from a human the host names (never the agent), and go stale after 15 minutes. An approval never widens a grant, never beats a revoked grant or a policy deny.

**What this proves:** the rules above, with fabricated agents and a fake provider (`tests/platform/test_authorization_gate.py`). **What it does not prove:** any live adapter, tenant, grant or client boundary. `live_proven` is always False and receipts say `mode=synthetic` unless the catalog row says `working`. The live proof stays with Jim's separate protected approval.

## Wired into the MCP servers (LIFE-865)

`lifeos/platform/mcp_access.py` puts `execute` in front of every tool call of `lifeos/buzz/mcp.py` and `python -m lifeos.inbox.send_to_jim --mcp` (a contract test fails if a handler skips it). The client is derived from a trusted fact only: the OAuth client a verified token names, or the OS user of the stdio server; an id, header, argument or environment variable from the caller is never read, and two clients with the same fact are refused as ambiguous (each client on a shared host needs its own OS user, tailnet node or scoped credential: LIFE-873). The purpose is the tool's, the tenant is the community's or workspace's, the request id is the server's. Grants live in `lifeos/platform/mcp_access.json` (seeded only with today's access, each with an expiry; revoke is one field) and the catalog rows stay `synthetic`: **not live-proven**. The Buzz release on Oracle carries `lifeos/buzz` alone, so a copy of `mcp.py` without the platform files refuses every tool call (`governance_unavailable`); adding the platform files to that release is the protected deploy step in `docs/buzz-remote-mcp-deploy.md`.

## Live proof (LIFE-865, Nov 22, 2026)

Deployed as release `52343c06da4e` of `lifeos-buzz-mcp` (all 13 files hash-matched on Oracle, dry load `clients 3 grants 12`, unauthenticated POST 401). Through the claude.ai Buzz connector (client `claude`): `buzz_capabilities` reported that release, `list_channels` answered for `life-os` and `bytalos`, and a call to community `tgp` was refused `community_not_authorized`. On the deployed release and its real data, run as `buzz-mcp` with a no-op effect: seven calls allowed (reads and the four publish grants, receipts `allow` then `ok`) and four refused with fixed reasons without running the effect (`catalog_unknown_capability` for send_to_jim and for an ungranted action, `catalog_unknown_principal` for tenant `tgp`, `identity_unknown` for a spoofed client).

**Live-proven (catalog status `working`):** Claude's `buzz_capabilities` and `buzz_read` for Personal, and its `buzz_read` for Bytalos. **Not live-proven (still `synthetic`):** ChatGPT's calls, every `buzz_publish` write (no post was made), Claude's Bytalos `buzz_capabilities`, and the `send_to_jim` server (no client has it configured). `live_proven` on the gate's outcome stays False by design; the catalog row status is the live-proof ledger. The service journal receipts were not read (a root journal read is not approved).
