## D113 — Amazon ingress: the Inbox and the Amazon label are not processed boundaries (2026-10-04)
The canonical Amazon Orders data source stopped at 2026-09-09 while Ordered/Shipped/Delivered mail kept arriving. Cause, reproduced in tests: the Gmail search was `{allowlisted senders} in:inbox -label:Amazon` and the census skipped any message already carrying the Amazon label. A Gmail filter that labels Amazon mail on arrival (or a person filing it) made the mail invisible to LIFE OS before it was ever recorded, and filing then looked like proof of processing. Fix: the sender allowlist is the only mailbox filter; the search is bounded by `after:` the newest `Latest Event At` in the canonical data source minus a 3-day overlap (45 days when the data source has no dated order; `AMAZON_SINCE=YYYY-MM-DD` overrides for a recovery). Idempotence belongs to LIFE OS: one order row per Order ID, Source Message IDs unioned, monotone lifecycle, so replaying the overlap changes nothing (`orders_same`, no write). A message already under the label and out of the Inbox is recorded but not refiled (`already_filed`); filing still follows a Notion write and read-back. No mailbox-wide rescan, second datastore, scheduler or TinyFish. The stage floor is 200 messages and an over-limit census fails closed before any write. `lifeos/amazon/projection.py` gives the Daily Command Center consumer a region-local PASS/NO_ACTION/DEGRADED from one run's counts (failure or review item means DEGRADED). The recovery is the same stage run from the watermark; its dry run reports counts and the live run waits for Jim's explicit GO.
