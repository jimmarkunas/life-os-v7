## D214 — A switchable cloud-Fit shadow, off by default, that never changes what Jim sees; the static Fit write keeps the cloud columns (2026-10-18, Jim; LIFE-41)
`lifeos.jobs.fit.cloud` (LIFE-41 10472 C with the 10474 corrections, under G1 10475). `V7_CLOUD_FIT` = off (default; unset or unknown is off) | shadow | canary | on; canary and on are refused with no call (G8). Off reads no store row and opens no connection. Shadow runs at the end of the Fit stage, after its static write, and asks Oracle's existing `fit1` verb through `edge.invoke` (same frame, request hash, nonce, receipt and `judge.accept` envelope; the base is the static result of the same text with the stage's profile, so the hard-family cap, the junior cap and the gate apply to the cloud score) for at most ONE job a tick (`MAX_PER_RUN` 1, Jim; `V7_CLOUD_FIT_PER_RUN` can only lower it to 0; a call starts only when the 240 s Fit budget still holds connect + reply wait). Candidates are new records only: READY or RESOLVED, a public employer / ATS posting (`source_kind` ats_api, jsonld, next_data or page_text: LIFE-41 10500; a title-only or title-watch placeholder is never sent), no Ledger page, static admission ADMIT or REVIEW, no private exclusion, never asked (`cloud_status IS NULL`), ordered by first seen and Stable Job Key; a PUBLISHED job is never asked, whatever later changes on it. V7 sends no profile text: the profile is a reference (`V7_CLOUD_FIT_PROFILE_REF`, 16 hex) to Oracle's own brief, so nothing is sent without it. The answer is stored privately in new nullable `v7_job_fit.cloud_*` columns (status, reason, score, confidence, rationale, request hash, model, run id, judged description fingerprint, time) by a separate UPDATE; the visible Fit, decision, admission, Ledger, Gmail, audit and Trash are untouched. Failures are fixed codes, `cloud_fit=DEGRADED(<code>)` in the counts line (no identifier or model text): a failure that is not about the one job (no host, an Oracle refusal including `LIMIT_UNCONFIGURED` and the G5 real-gate reasons, timeout, busy, hash/nonce/receipt mismatch, drift) writes nothing and stops the run's calls, so the job is asked on a later tick and no static score is ever shown as a cloud answer; an unusable judgment or an oversize request is recorded on its own job. The static write is now an upsert of its own columns (`INSERT … ON DUPLICATE KEY UPDATE`): `REPLACE INTO` deleted the row first and so wiped the cloud columns; `rejudge_excluded` marks a row stale (`model_version '0'`) instead of deleting it. No workflow sets `V7_CLOUD_FIT`, so every production tick runs it off; turning shadow on (G6) needs a separate workflow change (the variable, the profile reference and the tailnet join the fit-edge-test workflow already uses) and Jim's approval, as do G5, G7 and G8.

(4) An explicit `V7_CLOUD_FIT_PER_RUN` that is not a whole number fails closed to 0 (unset stays 1).
D214 and the installed Oracle contract (LIFE-41 10504, `front.py` 8e8d724b…): a `BUSY` reply, which carries no hash or nonce, is `FIT_EDGE_BUSY` (checked before the hash; `edge.invoke`, also on the fit-edge-test path); every installed refusal reason keeps its fixed code; the shadow reads with a 150 s wait (Oracle's real worst case is ~110 s) and starts its one call only when 165 s (connect + wait) remain of the Fit stage, by its own 240 s and by the tick's actual alarm (`signal.getitimer`), so a short tick never starts a call it cannot finish; a receipt's `purge` is absent (synthetic), `ok` or `failed`, a real reply (`fixture` REAL) must carry it, and `failed` is `FIT_EDGE_PURGE_FAILED`: the row keeps its provenance (model, run id, request hash) with no score and no further request is sent; nonces stay 32 fresh hex per request and the request hash is of the request as V7 sends it (with the 16-hex reference). ## D215 — Publish looks up Stable Job Keys in one batched Ledger query per 25 keys (2026-10-19, Jim; LIFE-76 saving 3)
Approved in LIFE-76 10437/10451 (saving 3). Before its loop, a live publish asks the Ledger once per `readback.KEY_CHUNK` (25) keys for every job it may publish (`publish._listed`, reusing `readback.ledger_pages`: an OR of exact Stable Job Key filters, paged; a missing or repeated cursor is refused). ## D216 — A board that has not changed is confirmed cheaply: conditional GET, a whole-board fingerprint skip and a quiet backoff (2026-10-19, Jim; LIFE-76 PR 2)
Canon LIFE-76 10428 §5. `http.fetch` now returns an answer's `ETag` / `Last-Modified` (`Fetched.validators`, a 304 included). For the boards one plain GET returns whole (`lister.CONDITIONAL`: Greenhouse, Ashby, Lever) the run sends the stored validators as `If-None-Match` / `If-Modified-Since`, and only when a skip is allowed; a 304 to them is `UNCHANGED`, a 304 nobody asked for is FAILED `ambiguous_304`, a host that ignores them answers a full 200 that is read as before, and every error path, paged board and other kind is unchanged. A COMPLETE listing whose whole-board fingerprint (`frontier_hash`, now computed over the board BEFORE the screen, so a screened-out job that leaves the board is never missed) equals the stored one skips the per-posting diff too. A skip reads and writes no item, writes no run row, and records the read as complete (`last_complete_at`, which the source alert reads). A skip is allowed only after a quiet full read (nothing added, changed, removed, admitted or pending) and never on every `WEB_FULL_EVERY`-th (4th) read, so a backlog, a screen change or a policy change is always seen within a few reads; any change resets the streak. A board that stays quiet is read up to `WEB_BACKOFF_MAX` (3) times less often (a daily seed board: every 3 days; LIFE-76 Part 2). Board cadence (`slot_due`): every board keeps one fixed phase of its period, hashed from its id from a fixed epoch, so a first pass that read thousands of boards in one hour does not leave them all due in the same hour again; the next read is the board's first phase at least half a period away, and a board read on its phase is read again exactly one period later (the average interval is unchanged; ~10,500 daily boards spread to ~440 an hour). New nullable `v7_sources` columns: `etag`, `last_modified`, `unchanged_runs`. Which hosts honour validators is measured on the real runtime in the first approved live window (counts `not_modified` / `same_frontier` per run); the container this was built in cannot reach the ATS hosts (proxy 403), which is not evidence about them.

## D217 — A board's first read belongs to a hibernatable backfill; the hourly board pass only re-reads (2026-10-19, Jim; LIFE-76 PR 3)
About 10,500 seed boards have never been read once. Their first reads no longer compete with re-reads in the hourly `boards` stage: that pass (`boards.run`, `select="known"`) reads only boards with a `v7_sources` row, plus the curated extras of boards.json. Known / never-read is classified against the persisted state; a board forced by the dispatch `report` input only skips the due-time check (and is read first, as a full read), so in one tick it is read once, by the pass its state belongs to. The first read is the `boards-backfill` stage (`boards.backfill`), the LAST bulk stage of the existing tick (no new workflow, scheduler or datastore), switched by the repository variable `BOARDS_BACKFILL` (default off: hibernated, it reads nothing and opens no store session). On, a run reads at most `BOARDS_BACKFILL_PER_RUN` (450) never-read boards in id order through the same screen, diff, admission budget (`BOARDS_INGEST_PER_RUN`), 429 stop and FAILED-is-never-a-removal rule; the resume cursor is simply "no state row yet", so an interrupted run resumes where it stopped and no board is read twice. A board it reads, COMPLETE or FAILED, gets its state row and from then on belongs to the hourly pass (a failure is retried there). Counts only: `read`, `errors`, `remaining`, `backfill` = off | on | drained; drained reads nothing. A quick proof run caps it at 50. It never gates the end-to-end path: it runs after every fast-path and hourly bulk stage, only while the run's time lasts.

## D218 — An interview request progresses only on verified round identity; a Ledger link needs a Stable Job Key or requisition (2026-10-19, Jim; LIFE-42)
`lifeos/interview/progression.py` is the pure step between a verified interview request and the existing D39/D40 writer: `progress(invite, rows)` returns the writer's `ParentQuery`/`RoundQuery` only when the company and role are present, the date is a valid ISO date, and an interviewer or a positive ordinal is supplied (the same rule as `creation_eligibility`); otherwise it refuses with `identity_invalid`, `round_date_missing` or `round_identity_incomplete`. It links a Job Ledger row only by an exact Stable Job Key or requisition match within the same company and role. A single company/title match is reported as `unverified` and is never linked; two same-title rows that no requisition separates return `requisition_ambiguous`; a Stable Job Key and requisition that name different rows, or a linked row recording a different value for the other identifier, return `identity_conflict`. Both refusals write nothing. The manual `interview-acceptance` stage is the production route: `acceptance.run` passes the secret's case through `progress()` before `stage.run`, refuses anything not `ready` as `acceptance_secret_invalid`, and adds the fixed Ledger code to its counts. It reads no Ledger rows (`rows=None`), so it reports `unverified` and never claims a link. Duplicate protection stays in the writer: a replayed request resolves to `child_match` with 0 writes, and the Live Notes and Raw Notes snapshots are unchanged. No new scheduler, datastore, workflow input or public identifier logging.

## D219 — Cloud Fit backlog: a bounded, resumable batch on the one Oracle fit1 path, run by hand or after each tick at Jim's count (2026-10-19, Jim; LIFE-41 10586)
*Recorded Oct 20 (the code cited D219 from Oct 19 but the entry was never written).* `python -m lifeos.run fit-cloud-backlog --limit N --live` (`lifeos.jobs.fit.backlog`) asks Oracle's existing `fit1` verb about jobs the tick's single canary call never reaches. **Bounds.** At most min(N, `V7_CLOUD_FIT_BACKLOG_MAX`, `cloud.BACKLOG_CALLS_MAX`) calls; the repository variable is Jim's ceiling and unset or invalid is 0, so nothing is asked (`BACKLOG_NOT_AUTHORIZED`). One request at a time: Oracle answers a second with BUSY, and concurrency 1 is never bypassed. Each call starts only when the batch's own time budget still holds it. **Candidates** (`cloud.BACKLOG_PICK`): the canary's predicates (D214, D226) without "never published", most useful first (Admit before Review, higher static Fit, newer posting). A published job's Ledger page is read first: Applied, an Applied On date or an unreadable page uses no call (`LEDGER_*` skip). **Exactly once.** A job is claimed by one conditional write before its call. The claim is released only when Oracle refused before any model ran (BUSY); anything after which a model may have run is recorded and never asked again. Each answer is written right after its call, so a batch can stop anywhere and the next resumes with the jobs still unasked. **Visible result.** An accepted answer is promoted through the Fit stage's promotion (D226), and the batch runs the unchanged `fit_sync` at its end. Jim set 20 an hour, under Oracle `fit1`'s daily cap of 480. **Budget** (#371, Oct 19): a batch that reaches its time limit after real calls is normal (`cloud_budget_reached`); the rest wait for the next run. A batch with no time for even one call is still `DEGRADED(STAGE_BUDGET)`. **Superseded part:** a published job the cloud would exclude was originally HELD privately with its page untouched; D224 replaced that with the normal exclusion.
