## D174 — The Daily Command Center reads V7 cards by their first line, and writes only its own region (2026-10-12, Jim)
The DCC kept calling fresh V7 cards "unverified" ("source-card timestamps do not prove end-to-end acceptance") and reported stale blocks nobody owned. Jim asked for a handshake between V7 and the ChatGPT task. Decision: `docs/DCC_CARD_CONTRACT.md` is the agreement, and its last section is the block to paste into the ChatGPT task's instructions (V7 cannot push into it). V7 promises that every region it writes carries an `Updated H:MM AM/PM CT` stamp in a fixed place and says `DEGRADED` or `STALE` in that same line when its stage failed or its snapshot is over 3 hours old; the DCC reads a stamp within 90 minutes of the page fetch as fresh, does not hedge a fresh card, reports a `DEGRADED` or `STALE` line as such, and writes only its own callout by the D169 procedure, returning PASS, NO_ACTION or DEGRADED with one fixed code. One-way in practice: V7 does not see whether the DCC ran (an option, not done: the DCC stamps its own first line and V7's daily check-in reports its age, which needs a Notion read in the watchdog). The stamp proves a card's stage ran, not that the world behind it is right. Not changed: any card, the page, the router contract (D58), or the DCC's ownership of its region.

## D175 — V7 writes the Daily Command Center (2026-10-12, Jim)
The Command Center was the ChatGPT task's (D58) because it was the retired system's prose summary layer, but that task's Notion connector can only edit page markdown (no block ids, no block-local write), so its write was refused or could not be proven (D169), and its text kept calling fresh V7 cards "unverified" and reporting stale blocks nobody owned. Jim asked for V7 to take it over. Decision: `lifeos/dcc/card.py` (stage `dcc-card`, job `dcc` in `domains.yml`) writes the callout as the last card of every tick. It reads the first line of each V7 card (Calendar, Jira, Bills, Mail Alerts, Amazon, Attention, Hiring Pipeline), judges each fresh (an `Updated H:MM AM/PM CT` stamp within 90 minutes), stale, degraded (`DEGRADED`/`STALE` prefix), unknown or unreadable, and writes five lines by rules: its own `Updated` stamp with how many areas are current, Current focus (the Jira card's GTV action and sprint lines, verbatim), Attention needed (overdue bills, active Attention exceptions, mail waiting or needing review, active interview opportunities, read from the cards' own counts), Evidence freshness (each card's time or state), and Next useful action (check any area not current, triage overdue bills, clear overdue or blocked Jira items, review Attention exceptions and mail). It uses the same block-local write as every card: the heading keeps its identity, only the old text is replaced, every other V7 region is proven unchanged around the write, and a wrong target, an unreadable protected region or nothing readable at all writes nothing (`DCC_NO_EVIDENCE`). No new data source, no model, no judgement a card did not already state; plainer wording than the prose it replaces. Needs the callout's block id as a Bitwarden secret named `DCC_CARD_BLOCK_ID` in the project the Actions runtime token reads (the job loads it like `NOTION_JIRA_TOKEN`; Jim added it, and a same-named entry in another Bitwarden project is unused). The router's owner name for the region is unchanged, and so is the heading text: renaming "ChatGPT · Daily Command Center" in Notion needs `router.DCC_REGION` changed in step, or the card refuses its target. The ChatGPT task must stop writing the region once this is live (Jim removes that section from its instructions), and keeps the Interview Advisor. D169's write procedure and `lifeos/platform/dcc_write.py` stay as a tested record and are no longer used by a writer; D174's card-reading rules still describe the stamps. Not changed: any other card, the scheduler (the job is a stage of V7's tick, D133), the router contract's three outcomes.

## D176 — The accepted Posting Date follows D4: the most trusted source, then the earliest date (2026-10-12, Jim)
PR #221 stopped a later read that finds no date from erasing an accepted employer Posting Date (`COALESCE`), but the same expression let any later non-null read replace it: a repost whose employer page now says "posted two days ago" would overwrite an original date 40 days old and make an old job look new. The authority already exists: D4 (decided) lists the sources of a posting date in order of trust (1 employer or ATS structured data, 2 the aggregator's page, 3 newsletter text, 4 email age) and says the earliest credible date is the original posting date; D6 (proposed) says a repost is aged by the original date so D5 still excludes it. Nothing new is invented. `enrich.accepted_date` now decides what `enrich.save` stores: a read with no date keeps what is stored; a source weaker than the stored one never replaces it and a stronger one does; between the same source the earliest date wins. `posted_source` follows the date that is kept and `posted_age_days` is the age of the kept date (a read that finds no date leaves it alone, as before). A date stored before `posted_source` was recorded counts as the employer's. Today every writer of `posted_date` is the employer or ATS tier (the aggregator and newsletter ages live in `posted_age_days`), so the weaker-source branch is a guard with tests, not a path production takes. The Fit stage reads `posted_date`, so a repost of an old job is still excluded there ("older than N days"); `save` still derives READY or EXCLUDED_STALE from the read in hand (the lane policy lives in `finish`), so such a job can sit as READY until Fit excludes it. Interpretation to confirm: an EARLIER date from the same source replaces a later accepted one (D4: earliest is original); if "older observation must never replace" was meant for earlier dates too, that is one comparison to change. Not changed: D89, company identity, Stable Job Keys, queue ordering, the freshness gate in `finish`.

## D177 — A READY job with a stored EXCLUDE decision is judged again, and a failed publish names its cause (2026-10-12, Jim)

The stuck_jobs alert showed 40 jobs. The read-only breakdown (alerts-open, now split by status, link, page, Fit admission and stop code) found 39 READY jobs whose stored Fit decision was EXCLUDE (oldest 184 hours) and 1 READY job with an ADMIT decision and no page (160 hours). The 39: the gate moves an EXCLUDE job to EXCLUDED_FIT only in the pass that scores it, and a job whose decision is current is never re-picked, so a job that returned to READY with an old EXCLUDE (an age or place rule since changed) sat READY for days; none could publish, because publish takes only ADMIT or REVIEW. Decision: with the gate on and live, the Fit stage drops the Fit row of every READY job with no page and an EXCLUDE decision, so the same pass scores it again and the gate either excludes it or admits it on the current facts (the mechanism the D111 title and place correction already uses; nothing is demoted on a stale decision). The 1: publish logged only a count (`failed: 1`) when Notion refused a create; the counts now carry the fixed error code and Notion's own error code (never a message body), so a job that fails every run says why. Not changed: the 1 ADMIT job itself (its cause is unknown until the next run names it), the stuck_jobs threshold, and the stopped-source rule for Open Jobs and Dice (a separate decision).

## D179 — Notion rich text is split by UTF-16 units, not Python characters (2026-10-12, Jim)

One admitted job failed to publish on every tick for about a week with `NOTION_HTTP_400 validation_error body.children[2].paragraph.rich_text[0].text.content` (the error code was first logged by D177). The read-only body diagnostic (`alerts-open`, PR #235) found the third block of its page body was a paragraph whose longest piece was 2000 characters but 2004 UTF-16 units, with no control, NUL, surrogate or private-use characters: `rich_text()` split every 2000 Python characters, Notion's 2000 limit counts UTF-16 units, and four characters outside the basic plane (emoji and similar) in one piece pushed it over. Decision: `lifeos.platform.notion_client.rich_text` splits so no piece exceeds 2000 UTF-16 units (a character outside the basic plane counts two), never splitting a character; plain text splits exactly as before (2000, 2000, 500 for 4500 characters) and an empty text is still one empty piece. The change is in the shared client, so every writer that builds rich text gets it. Not changed: the 100-piece cap, the limit itself, or any caller. Not verified until the next tick publishes the stuck job.

## D180 — The store tunnel names how it failed (MON-1.5 evidence step) (2026-10-12, Jim)

Four of about 14 hourly ticks on Oct 12 lost one lane (Jobright at 03:00, 04:00 and 10:00 UTC, Lensa at 14:00) to `STORE_SSH_NETWORK` while the other lanes opened the same tunnel in the same minute. Each failed lane died 46 to 47 seconds after its step started, which is exactly three attempts of the 10-second connect timeout plus the 4 and 12 second waits: all three attempts timed out. The code grouped every SSH timeout under one name, so the logs could not say whether the server answered and then dropped the connection (sshd connection limit or rate limit) or nothing answered at all (a firewall or route dropping packets). Decision, evidence only, no change to retry behavior: `lifeos.platform.db` now classifies a banner-exchange timeout, a connection reset or a connection closed by the server as `STORE_SSH_BANNER`, and a plain connect timeout as `STORE_SSH_TCP_TIMEOUT`; `STORE_SSH_NETWORK` stays for unreachable and no-route. Both new codes are transient and retried exactly like the old one (three attempts, waits 0, 4 and 12 seconds). Every failed attempt also prints one line, `store: attempt N of 3 <code>`, so a lane that gives up shows whether all three attempts failed alike. Counts and fixed codes only. Not changed: the retry window, the connect timeout, the lanes' start times, authentication and host-key errors (never retried). Next, once a few failures carry the new codes: if they are `STORE_SSH_BANNER`, stagger the lane starts or lower the number of simultaneous tunnels; if `STORE_SSH_TCP_TIMEOUT`, a longer retry window is the only lever on our side (both need approval).

## D181 — A sub-task under a finished parent no longer blocks the sprint rollover, and a rollover that keeps failing pages the phone (2026-10-12, Jim)

Matt's board (MEJ) did not roll to the new sprint on Monday Oct 12: every hourly `jira-rollover-scheduled` run failed `JIRA_CARRY_VERIFY_FAILED` for that board. Cause (read-only Jira search): the old sprint held MEJ-10, an unfinished sub-task, under MEJ-122, a parent already Done. Jira keeps a sub-task in its parent's sprint, so moving MEJ-10 to the new sprint never took effect, the rollover's check that every carried item arrived could never pass, and nothing was closed (as designed: it fails closed). The other board (JFM) rolled normally. The step is a warning by design, so nothing told anyone. Decision, two parts. (1) `rollover.split_unfinished`: an unfinished sub-task whose parent is not itself unfinished in the same sprint is stranded: it is left out of the move and the verification, counted (`stranded`, or `would_strand` in a dry run) and stays in the closed sprint, where Jira already keeps it. A sub-task whose parent is unfinished is carried and verified with it as before. The fetch now also asks for the `parent` field. (2) `lifeos/jira/watch.py`, new stage `jira-rollover-watch` run by the jira job right after the scheduled rollover step with that step's outcome (like D173): a live success records the time and closes any open alert; a live failure pages only once the rollover has not worked for 3 hours (three hourly runs), reminds every 6 hours and says when it recovers; a skipped step or a dry run records nothing. State is one private row in a new table `v7_jira_rollover` (schema change; precedent D173). The jira job loads one more Bitwarden secret, `NTFY_TOPIC` (the same entry the Outlook, Attention and Mail jobs use), and only the new step receives it and the database values: the rollover step itself still has none. Counts and fixed words only; alerting never changes the rollover's result. Nothing in Jira was changed by this work: the new code strands MEJ-10 on the next tick after merge (expect `stranded 1` for MEJ and no failure). Not changed: the schedule, the carry-forward and close/start order, the fail-closed checks, which boards roll, or whether a stranded sub-task should be re-parented or closed by a person.

## D185 — JOBS-1.1A: a worthwhile HOLD job gets one bounded recovery attempt, and a failed one is surfaced once (2026-10-13, Jim)
Jim approved bounded recovery for worthwhile unresolved vacancies. D70 is unchanged: a HOLD job is excluded after seven days. The only addition is inside those seven days. In the twelve hours from day 6 to day 6.5 of a HOLD (`updated_at` between 6 and 6.5 days old) the `expire-holds` stage gives a HOLD job exactly one more try through the existing path: back to NEW when it has no final link (the lane's resolver picks it), or to RESOLVED when it has a link and the page was unreadable (Enrich picks it), with one attempt left on each counter. Nothing else changes: the resolver, the link test, Enrich's title and JD proof, Fit, the lane policy, the duplicate check on the final link and publish all judge the job as they judge any other, so no job is published without a verified final link and its JD, and the job keeps its id, dedupe key and source. "Worthwhile" is deterministic and uses only stored facts: a link to retry (a stored source URL), a path back (a final link, or a source whose NEW jobs a resolve stage reads: jobright, lensa, linkedin-alerts, dice; a first-party or other source with no link has no reader and is excluded on day 7 as before), not a `closed` or `dup` reason, and still inside its lane's admission age (US Remote 14, Skilled Worker 14, Scale-Up 30, from the Posting Date, else First Surfaced); an unknown lane is not worthwhile. At most 25 jobs per tick. The attempt is recorded in the new nullable `v7_jobs.recovered_at` (added by `ensure_schema`, Jim approved the column; no new table, scheduler, provider or paid call). Idempotent: a job with `recovered_at` is never requeued again, and one that is on HOLD again is excluded at once as `unresolved_after_recovery` (terminal like `hold_expired`, so the newsletter mail can close). Jobs past day 7 and jobs that were never worthwhile are excluded exactly as before (`hold_expired`).
Exception path: the existing alerts layer. Detector `unresolved_terminal` (INFO) counts the jobs excluded as `unresolved_after_recovery` in the last 24 hours and carries the count only; `reconcile` opens it once, keeps it silent while the state is the same and resolves it when the window empties. Titles, companies and links stay in the private store (`fit-review` shows them on request). The expire-holds log adds `recovery_candidates` and `recovered`. Not changed: the seven-day policy, the 150/400 stage limits, first-party relink (D101), the hold-expiry of jobs that were never worthwhile. Known edge: a recovered job that later returns to HOLD for an unrelated bounce is excluded at once, not after seven more days.
Timeline (verified against `hourly.yml`): Step 7a (`expire-holds`, in the `finish` job after Enrich, Fit and publish) requeues at tick T. At tick T+1 the `jobright`, `linkedin`, `lensa` and `dice` jobs run their resolvers (limits 40, 150, 400, 15), which read NEW jobs of their own source ordered by attempts, newest first; a RESOLVED job is read by Enrich in the `finish` job of T+1 (limit 150, newest first). A job whose resolver outcome is `deferred` or `rate_limited` is not an attempt (existing rule) and waits for the next tick. A recovered job has the most attempts used, so under a queue longer than the stage limit it is read after the others; the queue order is not changed (it would need two more production files). Failure paths verified on MariaDB 10.11 with the production writers: a resolver failure, an Enrich failure and an Enrich mismatch each park the recovered job on HOLD, and the next `expire-holds` excludes it.
Liveness (PR review correction): a recovered job must not wait indefinitely behind a saturated queue. Recovery now starts at day 6 and stops at day 6.5, and a recovered job that is still NEW or RESOLVED more than `RECOVERY_HOURS` (12) after its `recovered_at` is excluded by the next `expire-holds` as `unresolved_after_recovery` (the same terminal state and alert as a failed attempt). `recovered_at` is written once and by nothing else, so the bound cannot be moved by another writer. The latest recovery (6.5 days) plus 12 hours is day 7, so the seven-day rule is never exceeded. A job that moved on (READY or later) is not touched. The attempt itself is not guaranteed under saturation: the job then ends safely, never published, and the alert counts it.
Scope clarification (Tech Lead, 2026-10-13): this is a single bounded return through the existing resolution/enrichment path inside D70's seven-day window, not a new retry-later subsystem. D1's final application-link and complete JD requirements remain mandatory.
Hotfix (Oct 13, first live tick): the read-back compared stored DATETIME values (whole seconds) with the stage's clock (microseconds), so a correct write raised `HOLD_READBACK_MISMATCH` and failed Step 7a. `hold.run` now floors its clock to whole seconds before any write or comparison; the read-back and its fail-closed behavior are unchanged. The writes before the failure had persisted (autocommit) and are valid; the next run does not repeat them.

## D186 — JOBS-1.1A: publish serves the strongest actionable READY jobs first, with a reserved share for the oldest (2026-10-13, Jim)
Jim approved prioritizing the strongest actionable READY opportunities. Publish took READY jobs oldest first and stopped at its per-run cap (60), so a strong new job could wait behind weaker older ones whenever more than 60 were ready. Only the order changes (`publish.order`); which jobs are eligible is unchanged and absolute (READY, no page yet, a JD, and with the Fit gate on an ADMIT or REVIEW decision, so a hard exclusion never publishes whatever it scores). Order, from evidence already accepted: admitted before Review (a Review job is never lifted by missing evidence: no score or no date sorts last, and it never outranks an admitted job), then the higher Fit score, then the newer accepted Posting Date (else First Surfaced), then First Surfaced, then id, so the order is deterministic. Bounded fairness: `n // 4` of each run's places (15 of 60) go to the oldest waiting eligible jobs by First Surfaced whatever they score, so a valid job is reached in a finite number of runs however many stronger jobs arrive. A run of fewer than four places (a manual limit of 1, 2 or 3) has no whole quarter, so it reserves one place for the oldest when the UTC clock hour is a multiple of four: hourly runs serve the oldest one run in four, and a run of four or more places is not affected by the hour. The ordering keys are read first and the long texts only for the chosen jobs. Not changed: acquisition order, Fit scoring and lane decisions, the Notion write and read-back, human-owned state, retention and identity.
Shadow mode (D186 amendment, same day): with `V7_FIT_GATE` not `true` the lane decision is recorded but not enforced, and publish's eligibility is exactly what it was: READY, no page yet, a JD, with no filter on the stored admission. A READY job whose stored decision is EXCLUDE is therefore still eligible in shadow mode (D177 moves such a job out only with the gate on and live). D186 does not change that: it only ranks such a job last (below ADMIT, REVIEW and unscored jobs), so a stored EXCLUDE never outranks an admitted job. `tests/jobs/test_publish.py` proves both settings on the same rows.

## D191 — The Fit admission floor is 72 in every lane (2026-10-13, Jim)

The Jobs OS canon fixes one universal Fit admission floor of 72 for every lane, but the code still admitted at 68: `lifeos/jobs/lanes.py` `FIT_FLOOR` and the scorer's Go / No-Go bar `GO_THRESHOLD` were both 68, a policy discrepancy. Decision: both now read one value, `UNIVERSAL_FIT_FLOOR = 72` in `lifeos/jobs/fit/__init__.py`. A job scoring 71 or less is never ADMIT on Fit grounds; at 72 or more it is ADMIT only if every independent gate also passes (closed vacancy, market, work mode, pay, posting age, route, geography, a title-only read, a hard exclusion). A job under the floor is stored with its real score and a Review disposition (`Fit N below 72`, and `(on Jim's keep list)` where that applies); an unscorable job is Review with no number. Unchanged on purpose: the Review band (below 60 is Exclude), and the D100 rule that a Fit under 68 with a second open question is Exclude, so a Fit of 68 to 71 with a second open question stays Review exactly as before. The lane policy version is NOT bumped, so no stored decision is re-evaluated by this change: existing rows keep their admission until a job is scored again for another reason or a separately authorized, counted promotion re-evaluates them. A Review disposition only changes the Ledger page's `Admission Status` and `Review Reason`; nothing is trashed, demoted, excluded or rewritten, and human-owned state (Applied, hiring, interview) is not touched. Effect on new scoring: a job at 68 to 71 that passed every other gate is now Review instead of Admitted.

## D193 — Recruiters: a LinkedIn notification needs recruiting evidence, and a recruiter's company, role and request are read from fixed patterns (2026-10-12, Jim)

Two rows on Oct 12 showed two defects of RECR-1.2. (1) A genuine recruiter email ("I'm with (OP)", "Role: 401044 - Technical Project Manager", "Would you be open to a 15–20-minute conversation?") produced a row with only the person: the company statement and the `Role:` line had no pattern, and `What they want` was deliberately never written. (2) A LinkedIn digest ("<Name> just messaged you") produced an Active recruiter row: any display name of the form "Name via LinkedIn" on a relay domain counted as a human message, so a name and a delivery channel were enough. Decision. Classification: on LinkedIn only (any member can message anyone; the recruiter boards keep their fixed-pattern rule), a named notification qualifies only with recruiting evidence in the sender's own part of it, before the footer that describes Jim: a headline naming a recruiter / sourcer / talent role, a first-person recruiter statement, a recruiter signature, or two fixed staffing-request signals; otherwise the verdict is UNRESOLVED `RELAY_RECRUITING_UNVERIFIED` (counted, no row, the underlying message is not judged irrelevant). Extraction: company also from a first-person statement ("I'm with (Acme)", "I work with Acme"; Title Case, five words at most, no generic noun, never a domain guess); role also from a `Role:` / `Position:` / `Job Title:` line with an optional requisition prefix, after the existing sentence pattern so no earlier key changes; `What they want` from fixed request patterns only (a call or conversation with its duration, resume, rate, availability, application information), evergreen and without relative days, blank when nothing matches, blank and Needs review when two durations conflict. Writer: the same page is enriched when an existing row for the same person and week was made from this same message (its Source URL equals the message link exactly, non-empty) and differs only by a blank company or role the message supplies (the corrected key must then resolve to exactly that page; two candidates are ambiguous; a Done row is kept, never duplicated; a different or missing source link is a different message and nothing is merged or overwritten); only blank fields are filled, never a human's value, never Done, Active or Needs review; every write is read back. Quarantine: `Active` is set false on a row only when its exact message link was passed to the stage and the row is the automation's own, still flagged for review, with every human field blank and the same actor as creator and last editor; nothing passes that list today, so past rows are not swept. Not changed: schema, secrets, workflow, schedule, mail access (read-only), the other boards, Done behavior. **Failure signal (review correction):** a live write or authoritative read-back that fails now ends the Recruiters stage with the fixed code `RECRUITERS_RECORDS_FAILED` and exit 1 (counts are printed first, the failure counted truthfully, nothing reported created or updated); this is stage-local in `lifeos/recruiters/stage.py`, so D182's publish-only exit in `lifeos/run.py` is unchanged. In `domains.yml` the step is `continue-on-error`, so it shows as the existing Recruiters warning and never fails the Jobs run. A dry run cannot fail on a write.

## D188 — The Hiring Pipeline heading carries its update time, like Calendar and Jira (2026-10-13, Jim)
