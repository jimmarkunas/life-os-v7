# LIFE OS Development Policy

**Status:** Canonical active LIFE OS V7 development methodology, owned by `jimmarkunas/life-os-v7`; the V1 and V2 implementations are historical references only. **Owner:** Jim Markunas; material changes require Jim's explicit approval. For runtime and schedules, Jim's current instructions and the current Production Contract (`jimmarkunas/life-os-automation/docs/life-os-production-contract.md`) remain binding, as the authority order in §1 states; the live V7 implementation/workflow is what exists. `LIFE OS Daily Runs` is retired, and V7's existing GitHub scheduled workflows are the sole scheduled executor; retirement does not transfer to V7 any capability V7 has not implemented. Repo supplements may add mechanics but may not override this policy.

**Machine bootstrap routing index:** V7 `AGENTS.md` and `docs/CODEMAP.md`. They are pointer-only and adds no product, runtime, roadmap, or architectural authority. Use it to select the smallest canonical source set before reading further.

## 1. Mission and authority

Ship useful behavior through a codebase safe to change in minutes, not hours: `user outcome → bounded mutation → targeted proof → land or stop`. The process must remain smaller than the product; stop and simplify when work becomes exploratory, historical, or process-heavy.

### UI/UX-first delivery — Jim-approved October 14, 2026

For every user-facing LIFE OS feature, **build and show the smallest usable UI in the intended surface first**, using clearly identified synthetic data where source integration is not yet authorized. Require Jim's UI/UX acceptance before expanding the backend. After UI acceptance, connect one approved source/data contract and prove end-to-end behavior; defer speculative adapters, abstractions, and infrastructure until the already-visible product requires them. A passing backend test without the accepted user-facing outcome is not product completion.

### Deterministic UI-first applicability and proof gate — Jim-approved October 14, 2026

Before a development package changes code, classify its user-facing effect against the exact approved Jira issue, owning product requirements, and current presentation surface. This is an **applicability decision**, not a new queue, review workflow, approval status, or documentation system:

1. **NEW or CHANGED UI:** Show the smallest functional preview **in the intended client/surface** using explicitly synthetic data where live data is not yet authorized. Include representative normal, empty, and degraded states where applicable. Obtain Jim's visual and interaction acceptance **before expanding backend implementation**. Static screenshots or attractive but inert controls do not prove working interactions.
2. **EXISTING UI, CHANGED RESULTS:** Keep the accepted layout. Before changing underlying logic, show representative **current versus intended output in its existing presentation format**, and establish the expected behavior with Jim where it has not already been explicitly approved. Reuse previously accepted product behavior and evidence; do not demand a new mockup or redesign for a data-quality, ranking, classification, or Fit correction. Protect the agreed examples with targeted tests.
3. **NO USER-VISIBLE CHANGE:** Name the existing downstream user outcome and the smallest relevant deterministic regression or operational proof. Do not fabricate a UI preview, request design approval, or block a bounded infrastructure-only change on an irrelevant interface gate.

After the applicable first gate, implement only the necessary approved vertical slice and prove **authoritative input → expected processing → actual destination**, including user interaction in the real client where relevant. Verify navigation, launch actions, state, and failure modes rather than treating a link, button, component test, or CI success as end-to-end proof. A preview is not permission to expose private data or broaden backend/source access; privacy and authorization gates remain independent.

Use the **existing Jira LIFE issue and associated PR** to record the classification, exact preview or representative output, Jim's applicable approval (or pre-existing approved behavior), and the final user-outcome evidence. No extra artifact, Jira workflow, QA hierarchy, scheduling, or coordination store is authorized. If required UI or changed-behavior acceptance is genuinely missing, stop the affected package as `BLOCKED: UI acceptance pending`; resume that same package after approval, rather than moving to another Jira issue. Existing approved outcomes must not be retroactively treated as missing approval. `LANDED`, passing tests, or a deployment do not establish product Done without the applicable real-boundary proof and Jim's final acceptance. Preserve the applicable execution boundary (including the Claude Code end-to-end mode below) and existing release, concurrency, and work-selection rules.

For private embedded UI, **first prove real Notion embedding and authenticated/non-public access with synthetic payloads**. Never assume that a private Notion page protects an independently hosted embed; never publish real message contents, contact identifiers or private state to GitHub Pages, anonymous URLs, URL tokens, public JSON, logs or artifacts. If the actual Notion client cannot render an authenticated/private embed safely, **stop and report the architecture/privacy blocker** rather than invent a separate server, auth workaround or public payload. Reuse the existing V7 hourly production tick for data updates, not a new scheduler. This UI-first order does not waive capability, privacy, ownership, release or approval gates; infrastructure-only work may use an evidence-first proof where no human UI exists.

Authority order: (1) Jim's explicit current instruction; (2) Production Contract for scheduled/runtime behavior; (3) this Development Policy for development method; (4) current Notion LIFE OS Platform canon for architecture/platform boundaries; (5) Jira Product Discovery `LOS` for approved product priorities and planning, and Jira Software `LIFE` for delivery backlog, status, blockers, dependencies, and sprints; (6) the exact owning current Notion product/domain canon for durable product requirements; (7) V7 `docs/MASTER_ROADMAP.md` as a dated technical WBS/evidence reference, not a second live planning board; (8) Development Projects only for ownership/concurrency/handoffs; (9) current implementation for what exists; (10) historical chats, handoffs, retired QA artifacts, old roadmap prose, and similar material only as background. A repo-local policy, `AGENTS.md`, or `CLAUDE.md` is subordinate unless this policy transfers ownership.

### LIFE Jira OS component and release versioning — Jim-approved October 16, 2026

LIFE's Jira Software components and Fix Versions use one OS-aligned scheme. This schema governs all LIFE issues and is the deterministic assignment rule for ChatGPT, Codex, Claude Code, and other authorized agents.

- **Component = owning OS.** Every LIFE issue has exactly one component. Use its owning product OS component; child issues inherit the parent Epic's component. Cross-OS work stays with one primary owning OS, while dependencies are represented with Jira issue links. Do not infer or change ownership from labels, assignee, status, or implementation detail.
- **Fix Version = that OS's target release.** Every LIFE issue has exactly one Fix Version whose name is exactly `<component name> X.Y.Z`, and the version's OS prefix must match the issue's component. Examples: `Jobs OS 1.0.0`, `Interview OS 1.0.0`, `Platform / Core OS 1.0.0`. Never assign a version belonging to another OS or use a shared platform release for an issue owned by another OS.
- **Issue creation and edits.** When creating a child issue, copy the parent Epic's component and Fix Version. When changing a parent Epic's OS component or target release, update its children only as part of an explicit Jira planning-owner decision; agents must not mass-move release scope. Existing LIFE issues were bootstrapped to their owning OS's `1.0.0` release on October 16, 2026.
- **Independent SemVer per OS.** Each OS advances its own version sequence. Patch (`X.Y.Z+1`) is for backward-compatible fixes or maintenance; minor (`X.Y+1.0`) is for backward-compatible capability; major (`X+1.0.0`) is for an explicitly approved breaking contract or baseline reset. Do not advance another OS's sequence when one OS releases.
- **Release authority and fail-closed behavior.** Only the Jira planning owner creates a new release, sets its release date/status, or changes an Epic's target release. Agents assign work only to an existing unreleased Fix Version on the owning OS Epic. If no such version exists, the component is missing or ambiguous, or component and version disagree, stop with `QUEUE_NOT_READY` and name the exact Jira field for the planning owner. Never invent a release, infer release readiness from status, or silently leave an issue without a matching version.

This Jira metadata records OS ownership and target release scope; status, blockers, dependencies, sprint order, and acceptance remain governed by the live Jira issue and this Policy.

### LIFE Jira issue-writing contract — Jim-approved October 29, 2026 (LIFE-79)

Every LIFE issue written or materially edited follows this contract. The field list is [`docs/jira/issue-schema.v1.json`](../jira/issue-schema.v1.json); the Notion **Jira Ticket Writing Guide** is a human companion, never a second policy. This section and the schema win over it.

- **Statement.** A Story: `As a [specific user], I want [capability], so that [benefit].` A Task or Bug: one bounded outcome (what will exist, for whom, where it ends).
- **Acceptance** is separate from the statement: one `Given [precondition], when [action], then [observable result].` per behavior, edge case or required UI state.
- **Record.** Jira is the execution and acceptance record; link the exact Notion requirement, do not copy it. Reference secrets by identifier only; never put a value in Jira.
- **Setup.** Tools and their purpose, execution host, setup state (`ready`, `not_required` or a prerequisite issue), owner.
- **UI.** Classify UI scope per the UI-first gate; for new or changed UI link the Figma frames or state why none apply.
- **UAT.** LIFE keeps the `Agent UAT` and `Human UAT` workflow statuses. Human UAT only with the label `needs-uat` (new user-facing UI or anything judgment-based): stop there with exact steps for Jim and record his acceptance. Otherwise the same-head CI and the local proof in the receipt are the proof and the agent moves the issue to Done.
- **Fast proof.** A deterministic fixture or clock test, a fixture replay of one recorded real input, or a dry run against fixtures, all runnable in CI or locally. A live, scheduled, on-demand or benchmark run is never a gate for Done; if one is useful it is a non-blocking watch (the next run happens anyway) and a fault it shows is filed as a Bug under LIFE-615. Where a rule can only be seen on real data, record one real input once and replay it as a test fixture.
- **Receipt.** One comment on completion: PR link, what changed, how it was verified (CI and local proof), and any live look not yet seen. The agent then moves the issue to Done; Jim reopens it or files a Bug.
- **Authorization, scope, assignment, and routing.**
  1. Jim's explicit, identifiable, authenticated instruction (ChatGPT, Claude, Codex or Buzz) naming the issue or Epic and scope authorizes it and need not be repeated in Jira. A connector- or agent-written comment may record it but is not proof; agents never invent, infer or widen an approval. An asynchronous handoff keeps its source (channel, issuer, time) and exact scope; if the authorization or scope cannot be verified, fail closed.
  2. `Agent Go` is the released queue for unattended pulls. Jim, a named human planner he delegated in Jira, or an agent under the self-promotion rule in Part 04 (LIFE-742) releases scoped work with transition ID 5 (To Do to Agent Go, "Authorize agent work"). Its `org-admins` restriction is not an agent-identity boundary (an agent using Jim's connector can invoke it), so the rule that **an agent never promotes an issue that names a protected step, or one outside the Part 04 rule, into Agent Go** is an operational policy gate, not a technical guarantee. A status change starts nothing: it wakes no agent, grants no credential and replaces no check.
  3. **Epic envelope.** Jim's approval of a named, finite feature Epic (key, outcome, criteria, boundaries) lets its lead and approved agents create and run the necessary in-scope children without a per-child approval, if each is created under the Epic with the required metadata, read back in Jira before execution, and passes every eligibility check here and in work selection. Creating a child never releases it; an agent releases work it created, leads or will execute only under the Part 04 self-promotion rule (never one that names a protected step). The envelope never covers a new product outcome, architectural override, another Epic or project, client data, or any secret, spending, permission, production or other protected action, and is never inferred from an Epic's existence, status, label or an agent comment.
  4. **Start.** Agent Go work starts with transition ID 14 ("Start work (authorization receipt required)") after a successful claim and every eligibility check; work Jim names, or inside an Epic envelope, that was never in Agent Go starts with ID 14 from To Do. Work returning from blocked, UAT, Done or Cancelled uses "Resume work". Eligibility: live issue, prerequisites, incoming blockers, lane, authorization provenance, permission scopes, active session, one-writer claim, permitted operations. The transition is not a security boundary; the limits are agent invocation, credentials, repository permissions and protected-action gates. It never authorizes out-of-scope work or another project (BAD/BPP need their own authorization).
  5. **Lanes and order.** Every actionable issue has a lane and an agent owner. Agents resume their own active issue, then take Agent Go work in their lane by Priority (highest first), Rank breaking ties; they never compete across lanes, self-assign unowned work or promote work outside the Part 04 self-promotion rule. Only independent issues run in parallel; an issue waits until every incoming `Blocks` predecessor is Done. Lane labels (`lane-career-v7`, `lane-edge-comm`) route only; `pull-ready` is retired.
  6. **Landing.** The assigned agent may implement, open a PR and merge a routine change once all required same-head checks and relevant proof pass and the repository's rules permit (Part 07 items 3 and 3a); an external independent review is not a universal prerequisite. Non-production deployment follows existing agent and environment permissions. Native GitHub approvals, protected actions, production access or writes, secret access, spending and permission changes keep their own controls; never expose a secret value. If this policy conflicts with live Jira or repository configuration, stop, report and await reconciliation.
- **Branch and PR names.** Branch: `life/LIFE-nnn/<slug>`. PR title: `[LIFE-nnn] <outcome>`. The PR body links the Jira issue and records its criteria, the validated head SHA, the proof and any exceptions.

- **No new ticket-management machinery (LIFE-767, Jim, Nov 16 2026: "nothing has moved in hours except for process theater" and "I want all 4").** No new stage, workflow step, label, status or check whose only job is to manage Jira tickets or process, unless Jim asks for it in chat. The existing `jira-fill` (LIFE-752, the last), `jira-stalled`, the readiness checks and `waiting-on-jim` stay as they are; deleting any of them is Jim's choice from the list on LIFE-767.

The UI-first, privacy, dependency, release, single-writer and final-acceptance rules are unchanged. A missing Done-when line or an unfinished `Blocks` predecessor means the issue is not ready (`QUEUE_NOT_READY`); other gaps are warnings.

### Deterministic agent work selection — mandatory when an authorized execution session starts or resumes

This is a **pull rule**, not a ChatGPT dispatch queue. When an authorized coding agent is invoked, resumes its package or finishes a Jim-accepted one, **the agent** picks the next eligible LIFE issue from live Jira. ChatGPT does not nominate issues or write handoff prompts. Instructions alone do not wake an idle session, and a Jira status change (including release to `Agent Go`) does not by itself start a dormant agent: use only an existing approved invocation, never a new scheduler, poller, watchdog or dispatcher.

1. **Resume first.** Fresh-read your active LIFE issue, its PR/head and, where writers may collide, your lane claim in Development Projects. An unfinished package is sticky until accepted Done, formally blocked or reassigned.
2. **Select from the Agent Go queue, not documents.** `project = LIFE AND status = "Agent Go" AND issuetype != Epic ORDER BY priority DESC, Rank ASC`, in your lane. Nothing outside Agent Go is selected autonomously, and an agent promotes work into `Agent Go` only under the self-promotion rule in the lifecycle section below. Skip, without any Jira change, issues with an incomplete incoming `Blocks` predecessor, missing or invalid owner or lane, a conflicting or already-claimed writer, an execution environment the agent does not support, a parked or unapproved product, another lane, or unverifiable authorization. A candidate needs an owning Epic, clear authorization (an individual approval, or a child recorded and read back inside an approved Epic's envelope) and a known lane. `To Do` or a linked LOS idea authorizes nothing. Release leaf issues only; an issue with children is a container.
3. **Order is Priority, then Rank.** Rank breaks ties, including at the default Medium. Humans set both; agents never reprioritize or reorder. No WBS order, creation date, key order or cached snapshot. A contradiction → `QUEUE_NOT_READY`.
4. **Start.** Re-read status, blockers and scope; keep one writer per mutation surface (Concord `start_work`/`finish_work` are optional, never a refusal). Make the supported transition Agent Go to In Progress (ID 14, "Start work (authorization receipt required)"), verify the read-back, then run the lifecycle below. Moving a ticket to Agent Go IS Jim's approval.
5. **Fail closed.** If access, authorization, lane, readiness, order or predecessors cannot be established report `QUEUE_NOT_READY — <exact gap>` and stop; do not ask ChatGPT to pick, invent a priority or use a snapshot. An empty `Agent Go` queue is `NO_ELIGIBLE_WORK` with no mutation and no pull from To Do.
6. **Completion.** PR/CI success is `LANDED`. After merge, receipt and read-back, the implementing agent moves the issue to Done (delegated closeout is the default); Jim reopens it or files a Bug. Then the same session repeats selection.

**Queue readiness.** Jira must hold usable lane ownership, curated order, truthful statuses and issue-level dependency and approval evidence; documenting this selector does not make a board executable. Repair planning data in Jira without creating another source of truth, and never mass-assign or reorder inside a development session.

**Lane labels (October 13).** `lane-career-v7` and `lane-edge-comm` identify the two authorized lanes; the lane label is the routing and ownership field and the assignee may stay Jim (agents are not Jira users). Only the Jira planning owner applies or changes lane labels, with one delegation: the approved lead of a specifically authorized project Epic acts as planning owner solely for new, in-scope children of that Epic (lane, owner, dependencies, Priority, Rank), verified by read-back before execution. It never lets an agent release into `Agent Go`, never reaches other tickets and never overrides blockers, acceptance, affinity or the one-writer claim.

**Release simplification — Jim-approved November 4, 2026.** (1) Jim's authenticated instruction naming the issue and scope starts that work without an Agent Go release; `authorization.provenance` records channel and time. (2) A whole `Blocks` chain may be released in one bulk transition; the links and this selector sequence it. (3) Readiness minimum: a valid key, at least one Done-when line (a Given/When/Then row or a bullet under "Done when") and every `Blocks` predecessor Done; everything else is a `warn` line (`python -m lifeos.sources.devtools.readiness`). (4) For an Epic Jim approved with a written non-protected scope, its approved lead may release in-scope children it creates into Agent Go; protected steps stay owned human Sub-tasks that block the work. This is the only relaxation of "agents never promote"; strike it to keep human-only release.

**Scoping.** One planning pass per Epic: write executable Tasks with Given/When/Then, a fast-proof command, `Blocks` links and protected-operation permissions, run the readiness validator on each, turn every gap into a fix or an owned human Sub-task, then stop; approved scope is not re-litigated.

**Delivery flow v3 — Jim-approved November 9, 2026.**
- **One ticket, one approval.** Moving a ticket to Agent Go is the approval and covers everything inside the written scope; at release the releasing session lists every approval the ticket is known to need (protected files by name, workflow edits, Oracle run lines, model spend, host steps, secrets) in one comment to Jim and records his answer as one `[approvals]` line (files, answer, `ct_stamp` time); a builder that finds a new need stops and asks once, naming it. A change of plan is an edit to the ticket plus one line `Scope change: <what> — Jim, <time CT>`; the description beats comments. A scoping note is one page (at most 2,000 characters: Outcome, 3 to 5 Done-when checks, Not in scope); one execution ticket is one PR or one sheet edit.
- **One receipt.** A builder opens its PR, waits with `gh pr checks <n> --watch --interval 30` and merges within 5 minutes of same-head green with `gh pr merge <n> --squash --match-head-commit <sha>`; if it cannot, it posts `[waiting on] <reason>` on the ticket. After merge post one comment: PR link, what changed, how it was verified, what is unverified. The agent moves the ticket to Done. Label `needs-uat` means stop at Human UAT with exact steps for Jim (new user-facing UI or judgment only).
- **Ticket truth.** The claiming agent edits its ticket in the same session that reality changes; a superseded ticket is Cancelled with a line naming its replacement. A session that claims a ticket posts `[claim] <session> <ct_stamp time>`; on any pause or hand-off it posts `[waiting on] <Jim, CI, another PR or ticket by key, a host step, or no free session>, <CT time>`, so no stretch of 60 minutes or more on an Agent Go ticket is unexplained (`python -m lifeos.sources.devtools.record_gaps FILE` lists such stretches from a saved Jira export; no timer, watcher or scheduled job).
- **Transitions.** Any status can reach any status so agents are never stuck. To Do and Agent Go reach In Progress only through ID 14; every other status uses "Resume work".

### Blocker Qualification Gate

`BLOCKED` is permitted only when a concrete dependency outside the approved package boundary prevents safe implementation or required deterministic proof. A blocker must prevent execution, not merely make execution less convenient.

3. prove the dependency cannot be resolved within the approved mutation boundary and execution budget;
4. complete every remaining non-blocked part of the package;
