## D249 — The recruiter brief is a read-only page on the Close service, built from the records on file when it opens (2026-10-24; LIFE-35 RECR-2.2)
**Why.** LIFE-35 asks for one compact derived recruiter brief from Mail, Recruiters, the Job Ledger, Hiring/Interview and Network evidence, and forbids another recruiter database, Fit score, hiring status, message archive or task system. V7 writes no Recruiters row page body today, and a new Notion write surface would need Jim's approval. **What.** `GET /brief?r=<Recruiters row>` on the private Close service (`outreach_app.handle_brief`, routed in `close_app.ROUTES`) reads through the gate's read-only client and shows seven lines, each from one record with its own source link or a fixed state: Who (person, employer, channel from the Source URL), Contact (first and last contact in Central Time, what they want), Role (the row's one `Job` relation, a page of the Job Ledger data source), Fit (that job's Why It Fits text, or "Fit not available"; never a score), Interview (the one Hiring Pipeline page for that job's company and role, its interview pages and section), Network (up to three of that job page's undismissed leads), Status (Action Status and follow-up date). No relation is "not linked", two are "more than one match", a source not read in full is "unreadable this time", never "none". It is built when opened and stored nowhere; nothing is written or sent. **Not in this change.** The link to it from the Recruiter Outreach table (a change to Jim's approved four-column layout, LIFE-20) waits for Jim; the live proof and Done are his.

## D250 — V7 reads and writes Notion only through databases and fixed IDs, never a page tree, an exact title or a page location (2026-11-07, Jim; LIFE-357)
**Why.** The one-page-per-job work (REQ-5) showed that code which finds a page by where it sits, what it is called or which pages hang under another page breaks the moment Jim reorganises Notion by hand. Pages Jim edits must stay free-form. **Decision.** (1) V7 reads and writes Notion only through a database (a data source row, found by a property or key) or a fixed ID held in the central secrets service or a named constant. (2) It never discovers a page by walking a page tree, matching an exact title, parsing a title into fields, or checking where a page's parent is; walking up from a configured ID (resolving the page of a block already held by a configured or stored ID) is allowed (Jim, Nov 7, 2026, LIFE-368); listing the children of a page held by a fixed or Ledger-row ID and verifying each child by its own machine identity (marker and identity block) is allowed (Jim, Nov 7, 2026, LIFE-382). (3) Pages Jim edits by hand stay free-form; V7 does not depend on their titles, order or location. (4) A machine region inside such a page is found by its own fixed marker or block ID, not by position or heading text. (5) Every new Notion integration proposal names the database or fixed ID it will use before it is built (the proposal is incomplete without it). **Scope.** New work follows this at once. Existing code that breaks it is listed by a read-only audit (LIFE-357), one LOS Idea per finding, and fixed only through its own ticket; this decision changes no code. The Hiring Pipeline page-tree paths are already being removed by the REQ-5 epic and are not re-listed. **Proof.** The decision index lists D250 and the full test suite prints OK.

## D251 — Every job gets the Bitwarden helper program from a saved, fingerprint-checked copy; the download, with a long retry, runs only when no copy exists (2026-11-08, Jim; LIFE-406)
**Why.** On Nov 8, 2026 (about 3:00 to 5:00 AM CT) GitHub's release download returned 504 and 502. `bitwarden/sm-action` (v3.0.1) fetches its helper program from that download at the start of every job, its own cargo fallback cannot work here, and D209's one retry after 30 to 74 seconds was built for Bitwarden refusing logins, so both tries fell inside the outage. Ticks failed at 3:00, 3:32, 4:00, 4:17 and 5:00 AM CT and domains runs at 3:05, 3:35, 4:03 and 4:19 AM CT. The "Authenticating ... exit 1" line that looked like a separate Bitwarden failure was the report job's own deliberate alert step (`FAILED LANES: finish`, exit 1) after the finish lane failed on the download.
**Decision.** D209 is extended, not removed. Every job that loads from Bitwarden (44 jobs, 88 loads, 21 workflows) first runs `./.github/actions/bws-helper`, one shared composite action, which puts the helper at the exact path the pinned action checks (`_actions/bitwarden/sm-action/<pinned commit>/target/x86_64-unknown-linux-gnu/release/sm-action`), so the action never downloads it. (1) GitHub's cache holds the copy, keyed `bws-helper-3.0.1-<hash of helper.sha256>`; the key contains no secret. (2) A copy is used only if its SHA-256 equals the fingerprint committed in `.github/actions/bws-helper/helper.sha256` (GitHub's published digest of the v3.0.1 Linux x86_64 asset, matched by a download on Nov 8, 2026); a copy that differs is deleted, never run, and the fingerprint is never read from the download. (3) With no copy the helper downloads, retrying with pauses of 10, 20, 40, 80 then 120 seconds until the job's wait budget (one third of its time limit, at most 600 seconds, set per job in `wait_seconds`) is used, then fails with a message saying Bitwarden was not contacted and nothing was guessed; a download that does not match the fingerprint fails at once and is discarded; a verified download is saved to the cache. (4) The load, pause and one retry pair (D209), the pinned action commit, `set_env`, masked outputs and every stage command are unchanged; no credential is read, passed or written by the helper, and it has no fallback source. The watchdog also has a dispatch-only test input `bws_test` (`normal` or `fail`) that skips the saved copy and points the download at an address that never answers, to prove the retry and the failure message.
**Proof (Nov 8, 2026, branch life/LIFE-406/bw-helper-cache, watchdog).** Cold run: cache miss, one download verified, copy saved, Bitwarden loaded with no download by the action. Warm run: cache hit, copy verified, no download, Bitwarden loaded. Forced failure: attempts at 10 and 20 second pauses, then the clear failure, Bitwarden never contacted. `tests/contracts/test_bws_helper.py` pins the wiring of all 44 jobs and runs the script against file addresses for the saved, retry, wrong-fingerprint and credential-free cases.
**Rollback.** Revert the squash commit; the cache entries can be left or deleted. **Open, not decided here.** Whether runtime Bitwarden should be replaced by GitHub's own secret store for jobs; that moves where secrets live and is a separate decision.

## D252 — Hiring decisions live on the Job Ledger row only: Confirm Rejected and Reopen are one Ledger write each, and no page moves (2026-11-08, Jim; LIFE-353)
**Why.** REQ-5 makes the Job Ledger row the job record, and LIFE-361 creates and finds that row for every interview pursuit. D195 closed a pursuit with no Applied row by moving its Notes page into a Retired Opportunities container; that is a second place hiring status lives, it depends on page location (against D250), and a pursuit the Ledger closed could not be reopened through it. **Decision.** (1) `decision.route` resolves a request to ONE Job Ledger row: the row whose page id the request names (its company and role must still agree, else `DECISION_STALE_IDENTITY`), or, when the id is not a row (an older opportunity page's own Manage link), the one pursuit row with that company and role (`DECISION_NO_MATCH` / `DECISION_AMBIGUOUS` otherwise). A pursuit row is one with Applied ticked or Stage set, so an interview pursuit's row (Stage set, not Applied) closes like any application. (2) Confirm Rejected (any of the six outcomes) sets Hiring Decision and appends one line to Hiring Decision History in one write; Reopen clears Hiring Decision and appends one Reopened line; a Hired outcome is reopened only with its own confirmation (`DECISION_HIRED_REOPEN_UNCONFIRMED`). A decision set by hand can be reopened the same way. (3) D194's safeguards stay: the request must be confirmed, the row is read, re-read just before the write and read back, and Applied, Applied On, Stage, Saturn Decision, Stable Job Key and Dismissed Outcome Ref are compared before and after. The operation id in the history makes a retry a no-op; a history line whose decision did not land is finished by the same operation (only the decision is written, never a second line); a line followed by any later decision is `DECISION_CONFLICT`. (4) Removed: `move_page`, the page listing, the Active/Retired container titles, the Move API version, the `DECISION_LEDGER_UNAPPLIED` guard and its screen, and the Notes-page path of the hand-set writer (holds, next actions and sent material are written on the row's `LIFE OS Hand-Set` property only). The hourly decide no longer reads `HIRING_PIPELINE_PAGE_ID`; auto-close reads the Ledger's pursuit rows only. Close links name the row id. The page tree is still read (out of scope here) to locate an older opportunity page for Manage and Mark Complete, never to decide. **Consequence.** A pursuit with no Ledger row cannot be closed, reopened or held from the screens (`DECISION_NO_MATCH`, nothing written) until it has a row. The decision number was taken without its claim tag: this session cannot push tags, and D252 was unclaimed on the remote when written.

## D254 — An edit in a machine-written section is preserved and repaired, never a permanent stop (2026-11-13, Jim; LIFE-658)
**Why.** A round page or opportunity page whose machine-written text had been edited by hand was refused for good (`machine_region_edited`): the page stayed stale, nothing on it said so, and the Interview OS step exited 1 every hour. Jim, Nov 13: the fix must be the long-term, hardened one, not a band-aid. **Decision.** Before anything in the machine region is rewritten, the differing text is copied verbatim and in order into the page's one "Preserved edits" toggle (created once; a round page keeps it at the bottom, an opportunity page directly above Jim's Notes because everything below that heading is Jim's), and read back; if that fails nothing is rewritten and the step stops with `preserve_failed` (`INTERVIEW_PRESERVE_FAILED`), retried next run. The region is then rewritten from the current render through the existing guarded write path (identity line last, protected-region proof, read-back; a failed rewrite rolls back and the copy stays). The page carries one "Repaired H:MM AM/PM CT" line inside its machine region, the counts carry `repaired_edits` (never `failed`), and every machine-written region shows a "Machine-written section: do not edit here" note. Only blocks inside the machine region are rewritten; a round page whose structure is not recognisable (a block or the identity line missing, another layout) keeps the old refusal and code. On an opportunity page the copied text is every line the fresh render does not carry, so a source change in the same run can add stale values next to the edit; nothing is lost. Not proven on a live page yet (LIFE-633). The decision number was taken without its claim tag: this session did not push tags.

## D255 — A no-board Scale-Up sponsor's job that passes the Scale-Up rules is posted from its listing page, as Review (2026-11-15, Jim; LIFE-723)

Result: 0% of 7 days published, the HOLD pile grew (48, 71, 73) and two quiet alerts ("Low yield: discover", "HOLD pile growing") stayed open. Jim, Nov 15: providers with no employer board should post to the job ledger provided the job is actually a fit for Scale-Up only; his answers: post with the listing link and the search snippet, tagged Aggregator Link; "a fit" means the Scale-Up rules only, no Fit score.
**Decision.** D1 and D36 are relaxed for this one case. After the existing chain (direct link, ATS board match, one employer search) has failed, a `discover` job held for `no_match_*` is posted from its listing page when its stated place is London or UK-wide remote (D96, D98) and it passes the hard title exclusions (D95; the private profile rules judge again in Fit). Code: `lifeos/sources/web/discover_jobs.promote_leads`, `lifeos/jobs/lanes.py` (`listing`), `lifeos/jobs/fit/stage.py`, `lifeos/jobs/audit.py`.

## D256 — Credentials and safety values are read from Bitwarden by the workflows; plain switches are read without masking, with fixed fail modes (2026-11-15, Jim; LIFE-704)
**Context.** LIFE-704 moves the 19 Bitwarden-bound GitHub values to Bitwarden (items lifeos/github-actions/<NAME>, created by Jim and the secrets service, LIFE-704 comments 13319 and 13320). The loader `bws-load` masks every value it loads, so a plain switch such as `true`, `on` or `22` loaded through it is masked everywhere and GitHub drops every job output that contains it (the LIFE-703 outage, Nov 15 2026). `LIFEOS_ACQ_SSH_PORT` was left a GitHub secret in EDGE-1.3 Phase B (#212) because it was not one of the 10 values migrated there (the commit says "not migrated"; the later comment "deliberately not in Bitwarden" records no reason, and none is written down).
**Decision.** (1) Credentials and identifiers (`BUZZ_STAGE_KEY`, `BUZZ_STAGE_HERMES_PUBKEY`, `BUZZ_URL_LIFE_OS`, `NOTION_FIT_SYNC_TOKEN`, `V7_ARCHIVE_TOKEN`, `OUTLOOK_CLIENT_ID`, `GMAIL_OAUTH_CLIENT_ID`) and the store's jump host and its known hosts (`V7_STORE_JUMP_HOST`, `V7_STORE_JUMP_KNOWN_HOSTS`, loaded as `LIFEOS_ACQ_SSH_JUMP_HOST` and `_KNOWN_HOSTS`) go through `bws-load`: masked, one retry, then the job fails, no other source. The jump values are addresses and a host key that can never equal a short switch, so masking is safe and keeps them out of logs. (2) The plain switches and numbers (`V7_LIVE`, `ALERTS_ENABLED`, `ALERTS_MUTED_UNTIL`, `ALERT_SETTINGS`, the five `V7_CLOUD_FIT*` names, `LIFEOS_ACQ_SSH_PORT`) go through the new `.github/actions/bws-plain` and nothing else: it runs the same fingerprint-checked helper with its output captured (no `::add-mask::` reaches the runner), reads only an allowlist, validates every value (enum, whole number in range, date, JSON object) and exports the validated value to the job environment. The log carries names and fixed codes only. (3) Fail modes when Bitwarden cannot be read or a value is refused: `V7_LIVE` is a dry run; `V7_CLOUD_FIT*` is off (no model spend); `ALERTS_*` stay on with the registry defaults (fail open: the alarm must not depend on the system it alarms about); `LIFEOS_ACQ_SSH_PORT` fails the job with `BWS_PLAIN_LIFEOS_ACQ_SSH_PORT_UNREADABLE`, with no GitHub fallback. (4) The watchdog gets an `alarm` job that uses only the run's GitHub token and opens one GitHub issue while the watch job fails (Bitwarden unreadable makes the watch job fail), so a Bitwarden outage still alerts. (5) `V7_STORE_VIA` stays a GitHub variable (it is not set in GitHub and has no Bitwarden item).
**Not done here, and why.** No GitHub value is deleted. The Oracle ticker (`lifeos/edge/ticker/ticker.py`) and the Alert settings app (`lifeos/sources/apps/alerts_app.py`) still read and write the `ALERTS_*` GitHub variables, so those three GitHub values stay until both move; until then a change made in the Alert settings app does not reach the workflows.
**Rollback.** Revert the PR; the GitHub values were never deleted, so the old reads work again at once.

## D257 — Bitwarden stays at three projects and three machine accounts; the alert switches live in LIFE OS ALERTS and the Alert settings app and the ticker use them (2026-11-16, Jim; LIFE-733)

The old layout (LIFE OS GitHub Actions, LIFE OS EDGE/OPENCLAW, LIFE OS EDGE/OUTLOOK) had no room for a fourth project, and the alert switches had to be writable by the Alert settings app and readable by both the workflows and the Oracle ticker. **Decision.** (1) The three projects are LIFE OS GitHub Actions (workflow values), LIFE OS EDGE/OPENCLAW (everything OpenClaw reads and writes, including the rotating Outlook and Todoist tokens, moved from the former EDGE/OUTLOOK on Nov 16 2026) and LIFE OS ALERTS (the renamed former EDGE/OUTLOOK: the three alert items). (2) The three machine accounts are GitHub Actions Runtime (read on GitHub Actions and ALERTS), LIFE-OS-ORACLE (read and write on EDGE/OPENCLAW and ALERTS) and one more account, unchanged by this change. (3) The alert items keep their ids (`lifeos/platform/alert_store.py`); the workflows read them through `bws-plain` (D256), the Oracle ticker and the Alert settings app through `alert_store` with a `bwsalerts` credential (a Bitwarden access token for the Oracle account, set to expire). (4) The OpenClaw wrappers' `OUTLOOK_PROJECT` constant is `LIFE OS EDGE/OPENCLAW`. (5) No fourth project or account is created; a new need goes into one of these three under `docs/platform/bitwarden-layout.md`.
**Rollback.** Move the five OpenClaw secrets back and restore the wrapper backups on the host (`*.pre-life733-20261115`); remove the `bwsalerts` credentials to put the ticker back on the repository variables. The three GitHub `ALERTS_*` variables are not deleted until a separate typed approval.

## D261 — Closed-unmerged and idle branches are archived then deleted; archive tags live in V7 as `archive/<branch>-pr<N>` or `-nopr`; deletes are off until Jim turns them on (2026-11-27, Jim; LIFE-1071)

Amends D244. D244 deleted a branch only when its PR merged, so branches whose PR was closed unmerged, or that never had a PR, sat in V7 for weeks, and the weekly report was read-only; on Nov 27 2026 Jim deleted 22 of them by hand and approved fixing both. **Decided.** (1) Archive tags are written to this repository, never to the retired system's repository: `archive/<branch>-pr<N>`, or `archive/<branch>-nopr` for a branch with no PR, created and read back through the Git refs API with the job's own `github.token` (`contents: write`). The old `v7-archive/` tags in the retired system stay where they are. `V7_ARCHIVE_TOKEN` is no longer read by any workflow; the Bitwarden item is left alone. (2) A pull request from this repository that closes unmerged follows the merged rule: tag the head, read it back, delete only when the branch head is still the head at close, no other open PR uses the branch, and it is not on KEEP. (3) The weekly report also sweeps every branch besides main and KEEP with no open PR and idle 14+ days (days since the last commit): tag, read back, delete after re-checking the head and the open PRs. Branches idle 7 to 13 days stay report-only; a branch with an open PR is never deleted. A tag that cannot be read back, or an existing tag on another commit, deletes nothing for that branch. (4) The first live run is a dry run. The switch is the one-word file `.github/branch-deletes` (`off` or `on`; anything else or a missing file is off). While it is off the run summary lists what it WOULD delete and nothing is tagged or deleted for unmerged and idle branches; merged branches are deleted as before. Only after Jim says "turn on branch deletes" is the file changed to `on`, by a pull request. (5) GitHub's "Automatically delete head branches" is on (Claude, Nov 27 2026); it removes a merged head branch at merge, and the archive job still tags the merged head. No new scheduler or trigger: the two existing ones, `pull_request` closed and the weekly `workflow_run`. Logs carry fixed codes and counts; branch names appear only on the run summary. **Rollback.** Revert the PR, or set the switch file to `off`; archive tags already written stay.
