# Off-site backup (LIFE-129, Jim, October 27, 2026)

Boot-volume backups stay in us-chicago-1 (cross-region replication is billed and not available here; a shared web host was rejected: its terms ban file storage). `lifeos/edge/backup/` adds a nightly, encrypted copy to Jim's Google Drive that does not depend on any Mac.

- **What:** an explicit list (`SQLITE`, `FILES`, `TREES`, `SECRET_TREES` in `offsite_backup.py`) of state that cannot be rebuilt: the Granola, OpenClaw state and agent databases (snapshotted by their owners through the sqlite backup API, never a raw copy of a live file), the OpenClaw config, the Fit and résumé config, the Close policy, and (Jim's decision, October 28, 2026) the OpenClaw credentials folder, so a lost machine does not mean re-linking every channel. About 11 MB.
- **Credential material:** collected from `SECRET_TREES` only (the OpenClaw credentials folder; files counted, never named). Every other list stays behind `DENY` (credentials, tokens, keys, `auth.toml`, Bitwarden, GitHub and Notion configs, systemd credentials), so a stray token file in a config folder is still skipped, and a test holds every non-secret list clear of it. This is safe only because the archive is encrypted to Jim's public key before it leaves, and the private key is never on Oracle. Bitwarden, GitHub and Notion credentials and the systemd credentials are NOT in the backup.
- **Encrypted before it leaves:** with Jim's PUBLIC gpg key (`/etc/lifeos-offsite/recipient.asc`). The private key is never on Oracle; the installer and the job both refuse a key file that carries a secret key. The plain archive is deleted before the upload starts.
- **Drive:** its own credential with the `drive.file` scope only (files this app creates; it cannot see the rest of the Drive), obtained once by `consent.py` on Jim's Mac and stored as the encrypted systemd credential `drive`. A wider grant is refused. Folder `LIFE OS Backups`; the newest 14 nightly copies stay; at most 3 removals per run.
- **Run:** `lifeos-offsite-backup.timer`, nightly at 2:30 AM Central, as root (Type=oneshot, no listener). `offsite_backup.py check` exits non-zero when the last run failed or is over 36 hours old; the status file holds counts and a fixed code only.
- **Install and rollback:** `oracle/install-offsite.sh` (`install`, `key`, `credential`, `dry`, `enable`, `run-now`, `verify`, `disable`, `uninstall`, `forget`). It touches only its own units, `/opt/lifeos-offsite` and its own two files.
- **Alert on a failed or missed night (Jim, October 28, 2026: quiet, phone only):** the job sends nothing itself. Oracle's `oracle1` answer (lifeos/oraclecloud/oracle/stats.mjs) carries the last result (`ok`, the fixed code, the age in hours); every tick the Oracle Cloud card shows `Backup ✓/✗` and `lifeos/oraclecloud/backup_watch.py` pushes `offsite_backup_failed` through the platform alerts gateway (INFO: phone only, reminded every 24 hours while broken, closed quietly when a good run lands) when the last run failed or is 36 hours old. An unreachable Oracle is unknown and changes nothing.
- **Restore:** decrypt with Jim's private key (his personal Bitwarden vault plus a paper copy), untar, and put each file back as its owner; the OpenClaw credentials come back with the rest; anything outside the list is re-created from Bitwarden and the sign-in flows.
